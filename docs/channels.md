# Channel adapters and verified principals

Every text surface (Slack, Microsoft Teams, email, built-in web chat) implements one contract, `platform/channels/text_channel.py`, so the coworker behaves the same everywhere and its authority always comes from a verified person rather than from message text.

## Contract

An adapter is transport-only. It implements `TextChannelAdapter`:

| Method | Responsibility |
| --- | --- |
| `parse_inbound(body, headers)` | Verify the provider's request signature, then return an `InboundMessage`: channel, conversation ID, thread ID, message ID, the verified sender (`ChannelIdentity`), text and attachment references. Raise `ChannelVerificationError` when verification fails. |
| `parse_approval_response(body, headers)` | Return an `ApprovalResponse` (request ID, `approve`/`reject`, verified responder) only for a verified structured interactive payload such as a button or card action. Free text is never an approval. |
| `send_reply(OutboundReply)` | Post a reply into the conversation/thread. |
| `send_receipt(ActionReceipt)` | Tell the thread what a governed Tool call did, with its ledger `requestId`. |
| `send_approval_prompt(ApprovalPrompt)` | Ask for an exact-action decision on one `requestId`. |

Attachments are references (ID, name, media type, size); content is fetched only through governed Tools.

## Principal mapping

`PrincipalDirectory` maps a verified channel user to a client identity from the EnvironmentBinding:

```yaml
channels:
  directory:
    slack:
      T01ABC/U02DEF: {identity: alice@client.example, roles: [approver]}
    teams:
      0f1e2d3c-.../4b5a6978-...: {identity: bob@client.example}   # <tenant id>/<Entra object id>, lowercase
```

- Keys are scoped by the channel workspace/tenant when the provider has one, so a user ID from another workspace never matches.
- A mapped user becomes a `member` principal with that identity and roles.
- An unmapped user becomes a `public` principal with a pseudonymous `unmapped:<channel>:<digest>` identity. Governance denies public principals every non-`read` Tool (`principal-not-authorized`, ledgered like any other denial) and they can never approve.
- `principal_for()` reads only the verified sender. Text that claims to be another user, an approver, or a system instruction has no effect.

The principal flows into governance as the initiating identity: `initiatingUser`, plus `originatingPrincipal` and `channel` in the bounded governance context, so the `requestId`, approval binding and ledger all name the real person. The governed sidecar takes a `principal_resolver` for this; when a channel gateway supplies one it replaces the static `MODEL_GARDEN_INITIATING_IDENTITY`, which remains the identity for runtime-only calls.

Channel approvals go through `decide_from_channel()`: the responder must be mapped with the `approver` role, and their directory identity, never anything typed in the message, is recorded as the approver.

## Voice (LiveKit)

The LiveKit Receptionist follows the same semantics. A phone caller is an unverified channel user: the SIP participant identity and caller number are transport facts, not a client identity, so a caller maps to a public principal and must never be treated as a client member. Today the voice Receptionist calls governed Tools with the runtime workload identity rather than a channel principal; its only write (`calendar.book`) requires exact-action approval by a human operator, so no caller statement can authorize a write. A deployment that verifies callers (for example a mapped staff line) maps them through the same directory under the `voice` channel.

### Call transcript

`platform/channels/call_transcript.py` records a two-way transcript of each voice call: ordered turns (`caller`, `agent`, and `human` where captured) with offsets, the text actually sent to TTS (interrupted replies stored truncated and marked), a closing outcome (`resolved`, `booked`, `message-taken`, `transferred`, `abandoned`) and a redaction count. Settings are `MODEL_GARDEN_TRANSCRIPT*`:

- A spoken disclosure plays first (`MODEL_GARDEN_TRANSCRIPT_DISCLOSURE`, default notice provided). Setting it to `off` makes the worker refuse to start unless `MODEL_GARDEN_TRANSCRIPT_LAWFUL_BASIS_OVERRIDE_OWNER` names the accountable owner, who is then recorded on every transcript. The deploy no longer relies on someone typing that name: set it in the EnvironmentBinding (below) and the owner must sign the lawful basis. If the notice cannot be played, the call's transcript is discarded.
- **Signed lawful-basis override (#107).** `scripts/deploy-reference-voice.py` reads `spec.channels.voice.transcript` from the EnvironmentBinding (`mode`, `retention_seconds`, `disclosure`, `redact_patterns`, `lawful_basis_override`) and builds the worker's `MODEL_GARDEN_TRANSCRIPT*` environment (`platform/core/lawful_basis.py`). `disclosure: off` with transcription on is accepted only with a `lawful_basis_override` of `{owner, basis, signature}`: an Ed25519 signature by the owner over the purpose, owner, basis text (at most 300 characters) and the client-environment (the Compose project name). The owner's public key must be in `governance.ownerKeys`. Create the key with `scripts/policy-signoff.py keygen`, then `python3 scripts/transcript-signoff.py --owner <identity> --basis "<why>" --project <env> --key-file <private key file>` prints the block to paste. A missing owner key, an unlisted owner, an edited basis, another environment's signature or a Policy rule sign-off replayed as a basis all stop the deploy before a call is taken. The deploy also runs the worker's own parser over the result, so any other unsafe combination fails at deploy too. This proves the named owner signed; it does not prove the basis is legally sufficient, and it does not cover someone editing the worker's environment after deploy.
- Payment card numbers (Luhn-checked) and client patterns (`MODEL_GARDEN_TRANSCRIPT_REDACT_PATTERNS`, a JSON array of regular expressions) are redacted before storage and recorded as counts.
- Records go to `MODEL_GARDEN_TRANSCRIPT_PATH` with mode 0600 in a 0700 directory and the same bounded retention as fallback messages (`MODEL_GARDEN_TRANSCRIPT_RETENTION_SECONDS`, default 7 days; `0` stores nothing). A write failure is logged by error type only, noted as `TranscriptWriteFailed` in the lifecycle log, and never interrupts the call.

The worker writes a deterministic **extractive summary** (`summarySource: extractive`: the caller's first words, the agent's last reply, turn counts and the outcome, from the already-redacted turns) and the caller's speech-to-text confidence when the model reports one. It stays in the transcript store; the post-call summary below is what reaches the CRM.

**Transfers.** When the worker transfers a call it calls `note_transfer()`: the outcome becomes `transferred` and the record carries `transfer: {offsetSeconds, turnsAfter, captured}`. Any turn still heard after the request is flagged `afterTransfer`. A LiveKit cold transfer removes the caller from the room, so normally nothing follows and `captured: false` says so; the summary states "what followed is not recorded" rather than implying a complete call. Speech between the caller and the person they were transferred to is not captured.

### Post-call summary

`platform/channels/call_summary.py` gives each call a short summary when `file-calls` runs. With a coworker configured (`MODEL_GARDEN_COWORKER_API_KEY` plus `MODEL_GARDEN_COWORKER_API_URL`, or `coworker.url` in the worker config) it asks the coworker through `CoworkerClient` (the Hermes API inside the client's network) to write two to four sentences from the redacted turns; the transcript is passed as data, the answer is bounded and redacted again, and the record is labelled `summarySource: model`. With no coworker, or if it errors, times out or answers nothing, a deterministic extractive summary (`summarySource: fallback-extractive`) is used instead. A summary failure never blocks filing. `--no-summary` files the plain outcome-and-size line.

The summary is the `summary` argument of the governed `crm.log-interaction` call, so the same exact-action approval and ledger apply as for any filing: an approver sees the exact text, and the approved action is the one that runs. A model words a summary differently each time, so the chosen text is kept (mode 0600, 30 days, `call-summaries.json` beside the conversation store) and reused; a waiting approval does not go stale because the step ran again. A call already filed is not summarised again. The fallback quotes redacted turns (at most 160 characters each), so with the fallback or a model summary the CRM note can contain what was said; the conversation timeline and the ledger hold only a digest and the source label.

### Filing finished conversations

`python3 scripts/client-operator.py file-calls --project-name <env>` (run on the client host) reads the voice worker's stored transcripts and files each call through the governed `crm.log-interaction` Tool of whatever CRM is bound (`platform/channels/conversation_filing.py`, executed in the governed-tools container by `scripts/runtime-file-calls.py`). It is idempotent on the `transcript:<callHash>` reference, so re-running after a retry or restart adds nothing, and a call a person has already assigned is not filed again. A caller's number is a transport fact, so every call goes to the `unmatched` queue for a person to assign (`client-operator.py contacts review|assign`); the summary is the post-call summary above (or the outcome and size of the call with `--no-summary`), and the ledger holds no personal data. Filings are ledgered as `runtime:conversation-filing`. With voice deployed beside the worker, the worker's `calls` job (every 120 seconds, `intervals.calls`) does the same without an operator: the voice overlay mounts the voice container's data volume into `governed-worker` read-only (`MODEL_GARDEN_VOICE_TRANSCRIPTS=/opt/voice/transcripts.jsonl`), so the transcripts the worker could not reach before are filed, summarised, put on the timeline and their write failures ledgered by the worker, which never writes to that store. The command stays for an operator who wants to run it by hand; both are idempotent on the same reference. The job is skipped with a clear report when the volume is not mounted or no Tier 0 contact log is bound. With no CRM bound the command fails closed rather than filing anywhere else, and the transcript stays in the worker's store, visible to the operator.

`file-calls` also reads the worker's lifecycle log and ledgers each `TranscriptWriteFailed` (a call whose transcript could not be stored) once as `transcript.write-failed`, with the error type, time and call hash only; re-running does not repeat it. The voice container has no ledger access, so it logs the failure locally by type and writes the `TranscriptWriteFailed` lifecycle event; the ledger learns of it when this step runs. The event holds the error type, time and call hash only, never transcript text (an error type that is not a plain identifier is replaced by `Unknown`).

**One call, one story in the ledger.** `python3 scripts/client-operator.py audit timeline --project-name <env> --call <callHash> [--request <id>,<id>]` shows every ledger event (authorization, approval, execution, hand-off, child requests) of a call together: the listed request ids (full or an 8+ character prefix, plus their child requests) and every event whose correlation id is `call:<callHash>`. A listed id with no event is reported under `missing`. `client-operator.py conversations timeline --conversation cv-... --project-name <env> --ledger` does the same from the conversation timeline, using the `action` entries (the call's recorded `requestIds`) and the call hash. Limit: the voice worker does not yet learn the request ids of the governed Tools Hermes called for it, so `requestIds` stay empty and the aggregation relies on the runtime tagging those calls with the `call:<callHash>` correlation id.

The support mailbox worker now records handled emails on the tenant's cross-channel conversation timeline (with verified sender matching to Tier 0 contacts when unambiguous). That timeline is **not** an external CRM sync. When `crm` is bound to the Tier 0 contact log the worker also files each handled email through the governed `crm.log-interaction` boundary (against the one contact holding a verified sender's address, else the `unmatched` queue), retries outages and tells the mailbox owner about a blocked filing (see the CRM filing section of [contracts](contracts.md)); filing to an approved upstream CRM remains open (#108/#115). A public sender cannot authorize contact creation or filing.

## Email

`platform/channels/email_channel.py` holds the parts of the email surface that decide who is writing and whether an approval is genuine; it opens no network connection. The channel gateway (`platform/runtime/gateway.py`) now serves the hosted web chat, the Slack and Teams endpoints, the approval-link page and an SMTP listener into the spool (`smtp_intake.py`); the mail provider, DNS and MX setup and live proof with real providers remain open (#84, #109); the credential-free intake spool for a client's own inbound address is below.

- **Sender verification.** A sender is verified only by the receiving server's own `Authentication-Results` header: it must carry the deployment's trusted `authserv-id`, there must be exactly one such header, and it must say `dmarc=pass` for the same domain as the single `From` address. Headers from any other server, a missing or ambiguous result, a second `From`, or a DMARC pass for another domain all yield an `unverified:` sender that can never match a directory entry, so it is public and read-only. The mail server must remove inbound headers that already carry its own `authserv-id`. Mapped senders are listed in `channels.directory.email` keyed by lowercase address. Nothing in the message text changes identity.
- **Threading.** `reply_headers` keeps `In-Reply-To`, `References` and `Re:` so replies stay in the sender's thread and strips header injection.
- **Loop protection.** `loop_risk` refuses an automatic reply to RFC 3834 auto-replies (`Auto-Submitted` other than `no`), bulk, junk or list traffic (`Precedence`, `List-*`, `X-Auto-Response-Suppress`), delivery reports and null return paths, no-reply/mailer/bounce senders, a malformed `From`, the deployment's own addresses (`own_addresses`) and our own reply marker. Every reply built by `reply_headers` carries `Auto-Submitted: auto-replied` and `X-Model-Garden-Reply`, so two coworkers cannot answer each other forever. `EmailChannelAdapter.should_reply(body)` returns the decision with the reason (it is `loop_reason(body)`, which counts nothing, followed by `consume_reply(body)`); `ReplyLimiter` (default 3, at most 20) then caps automatic replies per thread under a file lock that survives restarts, and a refused message never uses up the allowance. Counters are kept per thread indefinitely and are not erased with a contact. This is only the guard: no mailbox is read and nothing is sent until a provider adapter and a draft-first flow exist (#109, #90).
- **Built-in inbound spool.** `platform/channels/mail_spool.py` (`MailSpool`) is the intake side of a client's own inbound address when there is no mailbox to connect (#77, #84, #109). `scripts/runtime-mailbox.py <store> --address support@client.example ingest < message.eml` is what a mail server's pipe or delivery agent calls; it listens on no port and sets up no DNS or MX. A message is accepted only when `To`, `Cc`, `Delivered-To`, `X-Original-To` or `Envelope-To` names one of the client's addresses exactly (anything else is dropped and ledgered by reason and size, never stored), must carry exactly one `Message-ID` (the idempotency key, so an MTA retry stores nothing new), is at most 2 MB, and is kept as a private file named by digest (0600, per client, at most 5,000). The spool grants nothing: the sender is still verified only from the trusted `Authentication-Results` when `SupportMailbox` parses the message, so an unverified sender stays public. `drain(handler)` hands each message to `SupportMailbox.handle` at least once: leases expire and make a message available again, a handler that raises records only its error type and is retried with backoff, and after three failed (or crashed) attempts the message is quarantined as `dead` for a person (`requeue` is the explicit way back). `ingest` exits 0 for stored, duplicate, misdelivered and unusable mail (refusing would bounce a message to whoever forged the sender) and 75 (temporary failure) when the spool is full or unwritable so the server retries. Everything is deleted after the retention period (default 30 days). The index and ledger hold ids, sizes, states and error types, never an address, subject or text. It is not a `mail.*` provider (nothing is read, drafted or sent through it); the runtime worker drains and purges it on its clock.
- **Approval links.** `ApprovalLinks` issues an HMAC-signed, expiring token bound to one `requestId`, one decision and one approver address; spending either the approve or the reject token spends both for that request and approver (a private marker file per pair). It proves control of the approver's mailbox only: the approver must still be a mapped `approver` in the directory. Mail scanners fetch links, so the page behind one must require a POST confirmation that submits the token; never act on a GET. `platform/channels/approval_confirmation.py` is that page's request handler (pure: HTTP-shaped request in, response out; no server, mail or socket). A GET verifies the token with `ApprovalLinks.peek` (which spends nothing and refuses a used or expired link) and shows who would decide what, with an optional redacted summary of the request and one button; only a POST carrying the token in its body spends the link and passes the single `ApprovalResponse` to the governed approval path, which still requires a mapped approver. Form fields cannot change the decision, request or approver; a POST whose `Origin` is present and not the configured origin is refused; every page is `no-store`, `no-referrer`, unframeable, script-free and escaped. The success page appears only after the governed path returned; if it raised, the link stays spent and the page says the decision was *not* recorded and to ask for a new link. The channel gateway now serves this confirmation route; actual approver email delivery and live tenant proof remain open. The signing key (at least 32 bytes) is supplied by the deployment.

### Customer support mailbox

`platform/channels/support_mailbox.py` is the credential-free handler for one inbound message to a support or enquiries address (#109). It reads no mailbox and calls no model; the classifier, the answerer, the `mail.draft` executor and the CRM executor are injected. The runtime worker (`platform/runtime/worker.py`) wires it to the built-in spool: the coworker classifies and answers through the Hermes API server, answers come only from sections a governed `kb.search` returned, and a reply is stored as a Tier 0 draft for the mailbox owner, who is told it is ready.

- **Public sender, body as data.** The sender is whoever the receiving server verified (`email_channel.py`), mapped through the directory like any email; the handler records `principalAccess` and has no approval path of its own. The message text goes only to the classifier and the answerer, never to a decision, so nothing in an email can grant authority, change policy, pick the recipient or ask for a send.
- **Order.** Loop signals first (nothing is classified, drafted or filed), then a message already handled (a redelivery or restart gets no second draft; `MessageLog` keeps digests of Message-IDs only, recorded after handling so a crash can repeat a draft but never lose a message), then the category.
- **Categories.** `enquiry` and `booking` can be answered, `spam` is dropped, and `complaint`, `other`, an unknown label or a classifier that fails go to a person with no draft. An answer must come with the identifiers of the approved sources it used; no answer or no sources also goes to a person, so the coworker never answers from nothing.
- **Draft-first, to the verified sender only.** The only mail Tool called is `mail.draft`, addressed to the verified sender address; a sender whose address was not verified gets no draft because a forged `From` could point the reply at a third party. By default nothing is sent and the result says `approval-required`. A client may list `enquiry` and/or `booking` in `send_categories` so the handler *requests* `mail.send` for that draft through an injected governed executor (the result is `sent`, `pending-approval` or `not-sent`); the approval policy still decides, and `complaint`, `other` and `spam` can never be listed.
- **Reply limit.** The per-thread limit counts only replies that are really drafted, and a thread that reaches it goes to a person rather than going quiet.
- **Filed through the sync ledger.** Every handled thread, including those handed to a person, is filed with `crm_filing.py` as one email interaction with one ledger entry per thread (the digest of the thread's root Message-ID), no message text, and the `unmatched` queue unless a `contact_for` lookup names a contact. A CRM outage never stops the handler; the entry waits in the ledger. The audit hook receives `support-mailbox.handled` with the thread digest, status, reason, category and draft id only.

`mail.draft` takes only recipients, subject and body, so a draft carries a `Re:` subject but not `In-Reply-To` or `Auto-Submitted`; whatever sends the draft must add those headers (`EmailChannelAdapter.reply_headers`). Not done: reading the mailbox, the model classifier and answerer, serving `mail.*` from the sidecar, owner OAuth consent and the coworker's own mailbox grant (#110, #129), and live proof with a real mailbox.

## Slack

`platform/channels/slack_channel.py` implements the contract for Slack without a Slack app, token or network connection (#82 remains open; there is no live-workspace proof).

- **Every request is verified.** Events and interactive payloads need a valid `X-Slack-Signature` (`v0=` HMAC-SHA256 of `v0:<timestamp>:<raw body>` with the app signing secret, at least 16 bytes) and a timestamp within five minutes, checked before the body is read; stale, future, unsigned or tampered requests raise `ChannelVerificationError`. `handle_challenge` answers Slack's one-time `url_verification` only for a verified request.
- **What is answered.** Direct messages and `@mentions` only. Mentions are answered only in the channels listed in the deployment's `allowed_channels`; the bot's own and other bots' messages, edits and deletions, reactions and ordinary channel chatter raise `SlackIgnored` with a named reason. The sender is the reported Slack user and workspace, mapped through `channels.directory.slack` (`T01/U02`); message text never changes it.
- **Threads.** The conversation is the channel and thread (`thread_ts`, else the message `ts`); every outgoing message is posted into that thread. Files arrive as references (ID, name, type, size), never URLs or content. Slack redelivers events it thinks failed, so consumers should de-duplicate on `(conversation_id, message_id)`.
- **Approvals.** `send_approval_prompt` builds Approve/Reject buttons whose value is the exact `requestId`; `parse_approval_response` accepts only a verified `block_actions` payload with one of those two action IDs, returns the clicking user as the responder, and `decide_from_channel` still requires them to be a mapped approver. Receipts carry the ledger reference.
- **Scopes (least privilege) for the app the client admin installs:** `app_mentions:read`, `im:history`, `chat:write`, and `files:read`/`files:write` only once file deliverables are enabled. The bot token is held by the deployment's transport, never by this module. A reply that carries a deliverable posts a reference line (name, type, size, the artifact's `tier0:<tenant>/<id>` location and the start of its SHA-256) from `text_channel.attachment_from_artifact` and `describe_attachments`. With `gateway.slack.upload_files: true` (and the app's `files:write` scope) the file itself is also uploaded into the thread through Slack's external upload flow (`SlackTransport.upload_file`: an upload URL, the bytes to `files.slack.com` only and without the bot token, then completion into the channel and thread; at most three files per reply, 10 MB each); if the upload fails, that file falls back to its reference line. This is tested against a fake Slack only: no real workspace has received a file, and token lifecycle (#68) and live proof are not done.
- **Which files a reply carries.** The gateway attaches a deliverable only when the coworker's answer names its `tier0:<this client>/a-…` location (the coworker is told to include the `documentId` exactly as `docs.create` returned it) **and** the artifact was kept for the same mapped person who is asking. A reference to someone else's file, another client's, an invented id, or any asker who is not a mapped person attaches nothing, so a public caller is never sent a file. Each attachment is ledgered as `deliverable.posted` (channel, location, size, short digest; never the name or content) and each Slack upload as `deliverable.uploaded`. The same path adds the reference line on Teams and web chat; Teams has no file upload yet (it needs the bot's file-consent flow).
- **Create the app from a generated manifest (#82).** `python3 scripts/channel-app-manifest.py slack --origin https://<gateway public_origin> --name "<app name>" [--files]` prints the Slack app manifest (`platform/channels/app_manifests.py`): the three scopes above, the `app_mention` and `message.im` events, the events URL `<origin>/channels/slack/events` and the interactivity URL `<origin>/channels/slack/interactive`, with socket mode, token rotation and org-wide deployment off. In Slack choose *Create New App > From a manifest* and paste it, install it to the workspace, then give the signing secret and bot token to the deployment as the `gateway.secrets` `secret://` references. Slack's URL check needs the gateway to be reachable first. The manifest holds no secret, and creating, installing and proving the app in a real workspace is still to do.

## Microsoft Teams

`platform/channels/teams_channel.py` implements the contract for Teams without an Entra app registration, bot credential or network connection (#83 remains open; there is no live-tenant proof).

- **Verification fails closed.** Every activity needs a Bot Framework bearer token. Checking its signature needs Microsoft's published keys, so that step is an injected `verify_token` callable that returns the claims; there is no default and an adapter cannot be built without one. The adapter then checks the issuer, the audience (our bot's application id), expiry and not-before (five minutes' leeway), that the token's `serviceurl` claim equals the activity's `serviceUrl`, which must be https on an allow-listed host (`smba.trafficmanager.net` by default), and that the activity comes from an allow-listed Entra tenant. A verifier error is a refusal, never a pass.
- **What is answered.** One-to-one chats, and `@mentions` of the bot in the conversations listed in `allowed_conversations` (channels and group chats). Bots, the coworker's own messages, edits, reactions, typing, membership changes and ordinary channel chatter raise `TeamsIgnored` with a named reason. File attachments arrive as references (name and unique id), never URLs or content; the HTML copy and cards Teams adds are skipped.
- **Identity.** The sender is the Entra object id Teams reports, scoped to the tenant (`channels.directory.teams` key `<tenant id>/<object id>`, lowercase); message text never changes it.
- **Replies go only where we were spoken to.** The service URL for a conversation comes from a verified inbound activity and is remembered (in memory, bounded); a reply to a conversation never seen that way is refused, so nothing can make the coworker post to an arbitrary URL. Replies carry `replyToId`. After a restart the URLs are forgotten until the next verified activity, and proactive messaging is not supported.
- **Approvals.** `send_approval_prompt` builds an Adaptive Card with Approve and Reject `Action.Submit` buttons carrying the exact `requestId`; `parse_approval_response` accepts only a verified activity with that payload from a person, and `decide_from_channel` still requires the responder to be a mapped approver. Receipts carry the ledger reference, and deliverables are posted as reference lines as on Slack.
- **Least-privilege settings for the bot the client admin registers:** a single-tenant bot (Entra application in the client's tenant) with the Teams channel enabled and scopes limited to personal and team chats it is installed in; no Graph application permissions are needed for this adapter. Bot registration and credential lifecycle (#68), real token validation, file upload and live proof are not done.
- **Build the app package from a generated manifest (#83).** `python3 scripts/channel-app-manifest.py teams --origin https://<gateway public_origin> --name "<app name>" --app-id <bot Entra application id> --output coworker-teams.zip` writes the uploadable package: `manifest.json` (a bot for personal, team and group-chat scopes, `supportsFiles` false, no permissions, `webApplicationInfo` or tabs, and `validDomains` of just the gateway host) and placeholder icons to replace with the client's own. Register the single-tenant bot in the client's Entra tenant with its messaging endpoint `<origin>/channels/teams/messages`, upload the package in the Teams admin centre, and give the bot credential to the deployment as the `gateway.secrets` `secret://` reference. The output is byte-for-byte reproducible so a regenerated package can be diffed against the installed one. Registration, installation and a live message round trip remain open.

## Built-in web chat

`platform/channels/web_chat.py` is the authentication core and adapter for the built-in web chat (#84); the hosted page, HTTP server and sign-in email are in the channel gateway (`platform/runtime/gateway.py`), which is not live-proven.

- **Magic-link sign-in.** A sign-in token is issued only for an address on the client's allow-list (`issue_login` returns `None` for anyone else, so the page never reveals who is listed), expires in 15 minutes by default and works once; spending it returns a session token.
- **Scoped sessions.** Sessions are signed under a different label from sign-in links, expire (8 hours by default, at most 24), name the `client-environment` scope they were issued for, and are revoked by removing the address from the allow-list. A token from another client, environment or key is refused.
- **Authority from the session only.** `parse_inbound` and `parse_approval_response` take the sender from the `Authorization: Bearer` session; identities, names or approver claims in the JSON body are ignored. The identity is then mapped through `channels.directory.webchat`, so a signed-in but unmapped address is still public and read-only. There is no endpoint here that changes policy or approves for someone else.

## Action receipts

`send_receipt` is now used (`platform/channels/receipts.py`, `Gateway.announce_receipts`, #82, #83, #84). When `approvals.notify` names conversations, the gateway follows the Action Ledger and posts **one receipt per executed write, privileged or external-communication Tool call** to each of them, through whichever adapter (Slack, Teams, web chat) the conversation uses: the Agent, the Tool, `succeeded` or `failed`, an opaque object reference when the ledger holds a short safe one, and the ledger `requestId`. Reads, pending approvals, denials and other Agents' events make no receipt.

- **From the ledger, not the model.** A receipt is built from an `execution` event the governed boundary wrote, so it can only describe what really ran. It never carries arguments, results, titles, message text or an error message.
- **Once each, retried, restart-safe.** The gateway saves how far into the ledger it has delivered (`gateway/receipts.json`), starting at the end of the ledger the first time so history is never replayed. A receipt that reached no conversation is offered again, in order; what ran while the gateway was down is announced when it returns.
- **Ledgered.** Each delivered receipt is a `channel.receipt-sent` event (request id, Tool, outcome, how many conversations); a failed send is `channel.receipt-failed` with the channel and error type only.
- **Switch.** `gateway.approvals.receipts: false` turns them off (on by default whenever `approvals.notify` is set).

Not done: replying in the thread where the request began (the ledger does not record the originating conversation, so receipts go to the approver conversations), and any live Slack, Teams or web-chat run.

## The `inbox` command

A mapped team member who sends exactly `inbox` (or `/inbox`) in a **direct** conversation on any surface (built-in web chat, Slack DM, Teams chat) gets what is waiting for a person (`platform/core/inbox.py`, #77, #84, #88), answered by the gateway itself rather than the coworker:

- **Who sees what.** An approver or admin sees pending approvals (with a pointer to the Approve and Reject buttons), every open hand-off, open tickets (count and oldest age), unhealthy connections and records to review. Any other mapped member sees only the hand-offs assigned to them, each with the exact reply that closes it (`done <ref>` or `declined <ref> <reason>`), which the existing channel reply path records under their verified identity.
- **Authority from the channel only.** A public or unmapped sender, or a message in a shared channel, gets one neutral sentence and nothing else, so the command reveals nothing and cannot be used to probe what exists. Other words that merely contain "inbox" go to the coworker as before.
- **Non-sensitive by construction.** It names Tools, reasons, assignees, deadlines, short references and counts; never an action's arguments, a ticket's text, a contact or a message. Each use is ledgered as `channel.inbox-viewed` with the person and channel only.

Not done: a rich card or button view, and any live Slack, Teams or web-chat run.

## One contract, every surface

`tests/test_channel_contract.py` runs one compiled receptionist behind the email, Slack, Teams and web chat adapters and checks the same outcomes on each: the same mapped person gets the same identity and approval rights, a stranger is public and read-only whatever their text claims, a mapped member's write needs approval and names them and the surface, and only a mapped approver's structured click decides. The Agent definition is not modified by the surface. The Teams adapter passes the same suite, which is the "same Agent on Slack and Teams without changes" evidence; Teams file upload, bot registration and live-tenant proof remain open (#83).

## Status

The contract, directory and governance wiring are implemented and tested credential-free. The Slack, Teams, email and web chat adapters above implement the verification and identity rules credential-free and have no live proof; an email provider adapter (poller) and a hosted web chat page are separate stories and must implement this contract rather than bypass it. The support-mailbox handler has no mailbox poller, model or live proof either.

## Coworker memory in authenticated chat

The governed MCP surface exposes `memory_remember`, `memory_list` and `memory_delete` for mapped client members. Chat gateways must supply the verified `Principal` and an attested conversation identifier; without them, access fails closed. The model never chooses an identity, another conversation ID or another Agent's memory. Entries default to the current conversation; `agent` and `client` scopes are explicit. Lists include only the current member's entries; deletion is owner-only unless the transport-attested member has the `admin` role. Content is stored in the private governed volume; ledger events hold IDs and hashes, not text. Restricted content is refused by default until an authenticated, reviewed policy path exists. Admin export/purge remain operator-only via `runtime-memory.py`; this is not a public admin chat command. Runtime-native memory implementations may replace the store only if they preserve this contract.

`platform/channels/call_requests.py` gives a stored call its ledger request ids. The voice container cannot see the ledger and the governed runtime is not told which call a request belongs to, so the worker attributes by time: authorization events whose initiating identity is the runtime's own (`runtime:hermes`, not a named person, channel principal or scheduled task) inside the call's window, plus five seconds of grace. The record is labelled `requestIdsSource: ledger-time-window`. A call whose window overlaps another call's gets no ids rather than a guess, ids a record already carries are never replaced, and the transcript store is not written. Exact correlation (tagging each Tool call with `call:<callHash>`, which `client-operator.py audit` already reads) needs the Hermes API to forward a session id to its Tool calls; that is not assumed here.
