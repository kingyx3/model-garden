# Platform contracts

`contracts/v1/` is the compatibility boundary between the Model Garden platform, business-owned AI content and stable operational integrations.

Supported v1 business resources:

- `Agent` — composition of model profile, instructions, skills, tools and knowledge.
- `Skill` — reusable reasoning/instruction package.
- `ModelProfile` — logical model requirement mapped to approved candidates.
- `Tool` — executable enterprise capability with an explicit risk class.
- `KnowledgeSource` — approved source and data classification.
- `Policy` — client-owned approval rules, enforced by the governed boundary (see [Client approval policy](#client-approval-policy)); a dedicated policy engine remains out of scope.

**Model routing in the pinned Hermes runtime (v0.21.2).** A `ModelProfile` with multiple candidates must explicitly select `routing.strategy: ordered-fallback`: the **listed order** is primary first, then Hermes `fallback_providers` in order. The optional `priority` numbers are descriptive; reorder the list to change actual precedence. Provisioning fails closed on malformed/duplicate candidates or multiple candidates with a non-fallback strategy, rather than silently ignoring secondary models. The generated profile carries provider/model names only, **never provider API keys**; each provider must separately have valid approved credentials and cost/data-residency permissions before a live fallback is enabled. Hermes only attempts fallback for its supported provider-error classes; do not assume this guarantees availability. Verify provider-side fallback, cost attribution and authority boundaries in a live outage drill before making an SLA claim. The Hermes profile materializer also refuses symlinked/hardlinked managed targets and symlinked profile subdirectories, and atomically publishes mode-0600 files. This prevents an existing filesystem alias from redirecting fallback configuration or managed instructions into another coworker's files. Keep each profile directory private to its runtime owner: these checks do not protect against a privileged actor concurrently replacing ancestor directories, nor do they prove live provider isolation.

**Fallback attribution boundary (#243).** The governed Hermes MCP sidecar does **not** receive an authenticated per-turn selected-provider/model receipt from pinned Hermes. For a multi-candidate `ordered-fallback` profile it therefore omits `modelProvider` and `model` from its Tool authorization/ledger context rather than incorrectly asserting that the primary answered. This does not prevent fallback; it prevents false attribution. A single-candidate profile continues to report its configured provider/model (configuration, not a provider invoice). Model-level spend, identity and budget reconciliation for a fallback turn remain **unverified** until independently correlated provider usage receipts, governed request IDs and tenant-approved outage/exhaustion evidence are retained. Do not fill these missing fields from model text, client request parameters or an assumed primary provider. Existing exact-action approvals may need reauthorization because removing incorrect context changes the request ID.

**Shipped contract:** reusable `Skillset` catalogue packages group versioned Skills without granting Tool permissions or forcing activation. Each coworker explicitly selects enabled members; the compiler resolves dependencies and enforces independent readiness (details below). Business intent is defined in the [target architecture](https://modelgarden.atlassian.net/wiki/spaces/BA/pages/11796484).

## Capability contracts

`contracts/v1/capabilities.json` (validated by `capability-catalog.schema.json`) is the platform-owned catalog of provider-neutral Tool families: `chat`, `mail`, `calendar`, `files`, `docs`, `tickets`, `crm`, `code` and `kb`. Each portable Tool (for example `mail.send`, `tickets.create`) has argument and result schemas, a risk class (`read`, `write`, `privileged`, `external-communication`) and the argument fields that are safe to keep verbatim in the action ledger.

- `Agent` and `Skill` resources may declare `requiredCapabilities` and `optionalCapabilities`, naming a family (`calendar`) or a portable Tool (`calendar.book`). A required declaration on any selected Skill makes the capability required for the Agent.
- A `Tool` may opt in with `spec.capability: <family>`; its name must then be a portable Tool of that family and its risk must match the catalog. The reference `calendar.availability`, `calendar.book` and `crm.read` Tools do this with no behaviour change.
- The EnvironmentBinding selects a provider with `connectors.<family>.provider`; optional non-secret `tier` (0–4, default 1), `scopes` and `owner` describe the capability binding, **not** a coworker's credential. Approved upstream MCP/API operations additionally require an independently scoped, revocable per-coworker grant, reviewed connection and attested caller identity at the governed boundary (see [Per-coworker provider grants](#per-coworker-provider-grants) and [governed Tools](governed-tools.md)). This software path is offline-tested; separate downstream provider identities, consent/revocation and provider-native audit remain **real-tenant proof gates** ([#129](https://github.com/kingyx3/model-garden/issues/129), [#86](https://github.com/kingyx3/model-garden/issues/86)). Never reuse a shared provider token as a substitute.
- `compile-workspace.py --environment-binding <file>` resolves declarations: a required capability with no provider fails closed with a message naming the Agent, capability and environment; an unbound optional one compiles and is reported under `capabilities.degraded` with its fallback tier (Tier 4, human hand-off, until built-in Tier 0 storage exists; the `handoff_request` platform Tool prepares a write action for a named person, see [Human hand-off](governed-tools.md#human-hand-off-tier-4)). Docker deployment re-runs the same check against the real binding.
- The fail-closed message also names the Skill(s) that require each missing capability. With a binding, the compiled output carries `capabilities.skills`: one entry per selected Skill (plus the Agent when it declares capabilities itself) with `ready` and each dependency as `bound` (provider, tier), `missing` or `degraded` (fallback tier). It copies no token references, calendar IDs, scopes or owners.
- `compile-workspace.py --environment-binding <file> --readiness` prints that per-Skill table instead of compiling and exits non-zero if any enabled Skill is blocked. Disabled Skills remain visible for planning but are not executable.
- The coworker's runtime `platform.capabilities` Skill view is recomputed from its **actual deployment binding** rather than trusting a potentially absent or stale compiler snapshot. To keep disabled Skills explainable, compiled desired state may carry `disabledSkillDeclarations`: only non-executable capability names, never Skill instructions or Tool grants. Legacy disabled Skills with no recorded dependency metadata are explicitly blocked pending recompilation. Health changes (including revocation) update readiness without granting disabled Tools.

The `crm` family also carries `crm.create` (risk `write`) and `crm.log-interaction` (risk `write`: channel, direction, timestamp, summary, outcome and a transcript or message *reference*). Their ledger fields are object type/ID and interaction type only, never summary or transcript text. Only the Tier 0 built-in log (below) implements these Tools; HubSpot, Salesforce and Zoho have no native Model Garden adapters; all external CRM routes are planned upstream integrations under #93. Making the internal-record `crm.log-interaction` automatic while `crm.create`/`crm.update` stay approval-gated is a client decision: leave `crm.log-interaction` without `approvalRequired` on its Tool, or add a signed `allow` rule (below).

All of this is additive to `modelgarden.ai/v1`: existing workspaces without declarations validate and compile unchanged.

## Tier 0 business-rules knowledge

A `KnowledgeSource` with `spec.type: text-file` points at one `.txt` or `.md` file of approved business rules (`spec.file`, relative to the resource, at most 256 KiB, UTF-8, confined to the workspace or library root) so a small client needs no knowledge system. Optional `status` (`draft` default, `approved`, `retired`), `version`, `effectiveDate` and `audiences` (Agents allowed to ground answers) travel with it; these fields are rejected on other source types.

- Compiling an Agent that selects the source parses the file as an upload test and materializes it into desired state under `knowledgeContent` (content, SHA-256, section count). An empty, unreadable, oversized or escaping file fails compilation. `python3 scripts/knowledge-check.py rules.md [--query ...]` runs the same parse/test on an upload and shows what a search would cite.
- `platform/core/knowledge.py` splits the file into stable numbered sections (Markdown headings, recognisable plain-text headings, or paragraph chunks) and searches them. `search_selected` returns the `kb.search` result shape: each document carries its section citation (`knowledge:<source>#<section-id>`), source SHA-256 and version, and the result is flagged `dataOnly` (retrieved text is reference data, never instructions). Only content that is `approved`, effective today and addressed to this Agent is returned; otherwise there are no documents and a reason (`source-draft`, `source-retired`, `source-not-yet-effective`, `source-not-for-this-agent`, `no-matching-section`) so the caller clarifies or escalates.
- The governed `kb.search` runtime revalidates each materialized Tier 0 source's SHA-256, bounded UTF-8 text and parsed section count on **every retrieval**. Missing or changed compilation evidence returns `source-content-integrity` with no documents/read receipt; a caller should escalate rather than quote unverified rules. The generic `search_selected` helper retains an explicit non-strict mode for synthetic offline fixtures. A digest stored alongside content detects accidental or partial changes, **not** a privileged actor who can rewrite both the payload and its digest; this is not a signature, client approval or provider document ACL.\n- Each client/environment searches only the content compiled into its own desired state. `read_receipt` turns a result into section IDs and content digests for the existing governed read event (`record_knowledge_read` / `execute_action(read_receipt=...)`), so the ledger never holds the text.

**Runtime and activation.** The governed sidecar exposes `kb_search` (the `kb.search` Tool) over this module. It runs only when the Agent selected the `kb.search` Tool (see `examples/workspace/tools/kb-search.yaml`) **and** the capability manifest shows `kb` bound to `text-knowledge` at Tier 0; otherwise it refuses with "not connected here". Each search is a governed read: the ledger records provider `text-knowledge`, `tier: 0` and the section IDs and content digests, never the text. A client binds it with `connectors.kb: {provider: text-knowledge, tier: 0}` in the EnvironmentBinding; the registry lists it as `built-credential-free` (adapter `platform/core/knowledge.py`), so a Skill requiring `kb` is ready and the readiness report shows `kb: text-knowledge tier 0`. A deployment that selects `kb.search` gets the governed sidecar even with no calendar bound, and that sidecar holds no provider credential. This is credential-free build evidence only: no live deployment has exercised it.

**Conflicts and instruction-like text.** When approved sections on the same topic state different prices, amounts or clock times (across sources or inside one), `search_selected` marks each document `conflict: true`, lists the differing values under `conflicts` and returns guidance not to choose one but to say the rules need confirming and escalate; wording differences with the same facts, other topics and sections with no amount or time never conflict, and a draft, retired, stale or other-Agent source cannot create one. `check_source` warns the owner about the same conflicts at upload. Text that reads like an instruction to its reader ("ignore your previous instructions", "reveal your system prompt", "new instructions:") gets `contentWarnings: ["instruction-like-text"]` and an upload warning; it is flagged, never obeyed, and the result stays `dataOnly`. These are heuristics for the owner's attention, not a security boundary, and not a substitute for the governed boundary that already refuses actions the coworker is not authorised to take.

**Who a source may answer (v0.8.30).** The owner's `classification` now limits retrieval. `public` and `internal` (the default for an unlabelled source, and what the reference rules use) ground any answer, so existing workspaces are unchanged. `confidential` grounds only a verified, mapped team member: a public caller, a customer's email, or a call with no attributed person gets no documents and the reason `source-members-only`, so the coworker clarifies or hands off instead of using it. `restricted` is not served by the built-in store to anyone (`source-restricted`), because Tier 0 has no document-level permissions; it needs a provider that does, and a Skill whose only source is restricted reports `no-content` with a remediation saying so. The asker's standing comes from the sidecar's own principal, never from an argument (`kb_search` has no parameter that asks for more), and an unattributed call counts as public. `knowledge-check.py --classification` warns the owner at upload who a source could not answer. This is source-level, not per-document: it does not yet give document-level ACLs, cache invalidation on revocation or any external provider.

**Language and freshness signals.** A `text-file` source may carry `locale` (a language tag such as `en` or `en-SG`); `kb.search` takes an optional `locale`, matched on the language part, and skips sources labelled with another language (reason `source-other-locale`); an unlabelled source matches every request, and each returned section names its locale. When a request names a language that no source covers (every candidate was skipped as `source-other-locale`), the result also carries `availableLocales` (the declared tags of the selected sources, sorted and unique) and `localeGuidance`: do not translate another language's approved text and present it as approved in the requested one; say which languages are covered and answer in one of them, or offer a message or a person. The miss is noted in the unanswered-question store with its reason. This is a fallback rule for text only: it does not detect a customer's language, set an owner default, qualify a speech provider's STT/TTS languages or claim any language as supported (#239). Each returned section also carries `freshness`: the effective date, the `reviewBy` date, `reviewInDays` and `reviewSoon` when a review is due within 14 days, so an answer can say how current its basis is. These report the declared dates; they do not check the content is still true.

**Not yet delivered:** per-document permissions and cache/index invalidation, external knowledge providers, freshness refresh beyond `reviewBy`, and semantic (non-numeric) conflict detection (#116, #77). The reference receptionist declares `kb` and `crm` and its evals exercise both Tier 0 paths (see [Reference receptionist on a zero-stack client](#reference-receptionist-on-a-zero-stack-client)).

## Tier 0 document store

With `connectors.docs: {provider: built-in-artifacts, tier: 0}` bound, the governed sidecar serves the portable `docs.create` Tool from the private per-client artifact store (`platform/core/artifacts.py`, on the sidecar-only volume at `/opt/data/.modelgarden/artifacts`), so a client with no Drive or SharePoint still gets a kept document (#77, #101). It runs only when the manifest shows `docs` bound to `built-in-artifacts` at tier 0 (a forged tier, another provider or an unbound family is refused with the hand-off wording), and it is an ordinary governed write: the Tool is `risk: write`, so the exact call waits for approval unless a signed policy rule allows it, a public caller cannot use it, and the request is ledgered at `tier: 0` with `externalObjectRef` set to the document's `tier0:<tenant>/<id>` location. The document is plain Markdown by default (at most 200,000 characters, stored by artifact id so a hostile title cannot walk the filesystem, retained per the artifact retention period). The ledger holds the location, size and SHA-256, never the title or text (arguments are redacted); the same text from the same requester returns the same document. The result tells the coworker where the document is, not its contents; a person fetches it from the operator's artifact list (`client-operator.py artifacts`), and nothing posts a link to a channel or sends it anywhere yet. `docs.create` also takes an optional `format` of `docx`, `pdf`, `pptx`, `xlsx` or `csv` with `structure` in place of `content` (`sections`, `slides`, `sheets` or `rows`, as `platform/core/deliverables.py` defines them) and an optional list of `sources` identifiers (for example `kb:rules-of-engagement#hours`): the file is built by the standard-library builder and stored like any other artifact, the approval binds the exact format, structure and sources, and the ledger additionally records the format and source identifiers but never the structure's text. Spreadsheet text stays text (no formula runs) and decks and PDFs hold no links or active content. A provider that cannot build a format must refuse it, never fall back to text. Native Google/Microsoft formats are not part of this, and there is no live deployment evidence.

**Private filesystem trust (v0.8.171).** The Tier 0 artifact root and tenant directory must be private directories owned by the runtime UID. The lock, index and artifact payloads must be private, single-link regular files owned by that UID; symlinks, hardlinks, nonregular files, foreign ownership and group/world permissions fail closed before a read, duplicate response, delete or expiry. The index is size-bounded, opened without following links and published through an unpredictable exclusive temporary file; an index replaced during the transaction is refused. Existing deployments with permissive legacy artifact paths require an authorized operator to inspect ownership and tighten permissions before restarting. These checks are local filesystem safeguards, not independent storage provenance, backup erasure, provider-side identity or live client proof.

## Tier 0 work items

With `connectors.tickets: {provider: built-in-tickets, tier: 0}` bound, the governed sidecar serves the portable `tickets.search`, `tickets.create` and `tickets.update` Tools from a private per-client list (`platform/core/tickets.py`, `<governance root>/tickets/<client>.tickets.json`), so a client with no Jira, Linear or GitHub still has one durable place for "a person has to look at this" (#77). It runs only when the manifest shows `tickets` bound to the built-in provider, and every call goes through the normal policy, approval and ledger path: `tickets.create` and `tickets.update` are writes (a person's approval by default), `tickets.search` is a governed read whose ledger event holds ids and digests only.

- **Who sees what.** A verified `member` searches every ticket (with description and history) and is the only one who can update. Anyone else searches only the tickets they opened and sees title and status. A public sender reaches `tickets.create` only through a signed rule that names `public`, like any other public write. The tickets are shared by every Agent of the client (each is recorded with the Agent that opened it).
- **Idempotent and closed.** A ticket id (`t-<12 hex>`) is derived from project, title, description and opener, so a retry returns the same ticket (`duplicate: true`). The lifecycle is `open`, `in-progress`, `waiting`, `done`, `cancelled`; `done` and `cancelled` are final and every change records who made it. Text is bounded, card numbers are redacted, and the store is mode 0600 in a 0700 directory.
- **Ledger.** The contract's `ledgerFields` put the project, ticket id and status in the event; the title, description and comments are never in the ledger, and each result carries `externalObjectRef` `tier0:tickets/<client>/<id>`.
- **Where a person finds them.** The runtime inbox (`runtime-inbox.py`) adds an "open tickets" line with a count and the oldest age (no text), and `runtime-tickets.py list|show|update` is the operator command on the client host; an `update` is ledgered as `ticket.update` under the named person with the id and status only.
- **The support mailbox uses it.** When the built-in store is bound, every customer email thread handed to a person (a complaint, "other", no approved answer, a thread at its reply limit and so on) also opens one ticket carrying the thread reference, category and reason, never the message text, ledgered as `ticket.opened` by the platform; the same thread and reason give the same ticket and a failure never loses the thread.

An `inbox` message in a direct chat conversation shows a mapped team member what is waiting, including the open-ticket count (see `docs/channels.md`). Not done: a chat view of the tickets themselves (the coworker's `tickets_search` answers that), a retention rule for old tickets, projects or assignment, and any live proof (#77).

## Tier 0 contact and interaction log

With `connectors.crm: {provider: built-in-crm, tier: 0}` bound, the governed sidecar serves `crm.create`, `crm.log-interaction` and `crm.read` from a private per-client store (`platform/core/contacts.py`, on the sidecar-only volume at `/opt/data/.modelgarden/contacts`). Nothing is refused less strictly than a connector would be: each tool runs only when the manifest shows `crm` bound to `built-in-crm` at tier 0, is ledgered at `tier: 0` with an external object reference such as `built-in-crm:interaction/i-...`, and never writes names, numbers or summaries to the ledger (arguments are redacted, results are digests, reads record section-style record IDs and content digests).

- **No merging on an assertion.** `crm.create` always makes a new record whose identity evidence is `asserted`. A colliding phone or email adds the pair to a human review queue; the response never says so, so a caller cannot learn that a number belongs to a customer.
- **No guessing a contact.** `crm.log-interaction` files against a record ID the coworker holds, or `unmatched` for a person to assign; an unknown ID is an error. Interaction IDs are derived from their content (contact, type, channel, direction, timestamp, and the transcript reference or summary digest), so a retry, redelivered event or restarted worker returns the same ID with `duplicate: true` and writes nothing.
- **No read-back to unverified principals.** `crm.read` returns records only when the governed boundary reports a verified `member` principal. A phone caller (the voice channel still uses the static runtime identity), an unmapped sender or any other principal gets `requires-verified-staff-principal` and no data.
- **Bounded and private.** At most 5,000 contacts and 20,000 interactions, bounded field lengths, payment card numbers redacted from notes and summaries, files mode 0600 in a 0700 directory. Records are plaintext at rest on the sidecar volume, like the ledger and approval store; encryption at rest and retention schedules are deployment concerns.
- **Policy.** The example `crm.create` Tool is approval-required (and the default policy's `*.create` rule agrees) and the example `crm.log-interaction` Tool is not, matching "an internal record". Public principals can do neither (the platform floor).
- **People review and erase.** `python3 scripts/client-operator.py contacts review|assign|dismiss|erase-contact|erase-interaction --project-name <env> [ids] --by <person>` runs `scripts/runtime-contacts.py` on the sidecar. `review` prints personal data for a person to act on. Every change writes a chained `operator-action` event naming the person and the IDs, never the record contents; the identity is as asserted on the command line.

`crm.update` and object types other than `contact` are not implemented at Tier 0; selecting `crm.update` fails closed at provisioning. The `examples/workspace` `log-conversation` Skill describes the intended behaviour (file after each call or email, `unmatched` when unsure, never read back, short factual summaries); no example Agent selects it yet. **Not delivered:** wiring the voice transcript or support mailbox into filing (#107, #109), cross-channel timelines and CRM-outage reconciliation (#115), third-party CRMs (#93), retention schedules, and any live proof.

## Client approval policy

`Agent.spec.policies` names `Policy` resources whose ordered rules the governed boundary enforces for that Agent. A rule has an `effect` (`allow`, `deny`, `require-approval`) and optionally `actions` (Tool names or globs such as `calendar.book`, `*.send`, `crm.*`), `dataClassifications`, `channels` and `principals` (`member`, `public`).

A fourth effect, `human-only`, forbids automation: the action is prepared for the rule's required `assignee` (optional `deadlineHours`) as a Tier 4 hand-off instead of being executed (see [Human hand-off](governed-tools.md#human-hand-off-tier-4)). It is restrictive, so it covers every principal and an unknown channel or classification, and removing it counts as relaxing control in a policy diff.

Precedence is fail-closed:

1. a matching `deny` rule wins, then a matching `human-only` rule (nothing is executed, whatever else matches);
2. the Agent's `approvals.externalActions: required` and any matching `require-approval` rule always win over an `allow` rule (the stricter source wins);
3. `privileged` Tools are never auto-approved, and a public principal can never reach `privileged` or `external-communication` Tools;
4. a Tool's own `approvalRequired` default is waived only by a matching `allow` rule that carries a valid client-owner sign-off.

With no policy, Agent and Tool settings behave exactly as before (plus the `privileged` floor in point 3). Restrictive rules cover every principal and an unknown channel or classification; an `allow` rule covers members only unless it names `public`, and never matches an unknown channel or classification. A public principal may be given one named `write` Tool (for example booking inside published availability) only by an explicit `allow` rule with `principals: [public]` and a sign-off.

**Owner sign-off, checked at compile and deploy time.** An `allow` rule that relaxes an approval requirement (it matches a non-read Tool, or names `public`) must carry `signoff: {owner, ruleDigest}`. `ruleDigest` is the SHA-256 of the rule's canonical JSON without `signoff`, so editing the rule invalidates the sign-off and compilation fails, printing the digest to re-sign, until the named owner approves the new content. The runtime re-checks the digest before it honours an `allow`. Protect the sign-off lines with `CODEOWNERS` in the client repository so only the named client owner can change them; the platform checks that a sign-off exists and matches the rule, not who typed it. An environment can narrow who may claim to be the owner by naming them in its EnvironmentBinding (`governance: {owners: [owner@client.example]}`): compilation then also refuses a relaxing rule whose `signoff.owner` is not on that list (matched ignoring case and spacing), and an empty list refuses every relaxing rule. The list lives in the binding so it can be protected separately from the policy file (for example under different `CODEOWNERS`); it limits which names may sign but still does not authenticate the person, and it is checked at compile time, not by the running sidecar.

**Authenticated sign-off (v0.8.22; v0.8.149 schema interoperability fix).** An environment can also list its owners' public Ed25519 keys (`governance: {ownerKeys: {owner@client.example: <base64 key>}}`). Compilation then refuses a relaxing rule unless its `signoff.signature` verifies, with the key listed for `signoff.owner`, over that owner name and the rule's exact content digest, so a name typed into a client-editable workspace is no longer enough, and a rule edited after signing, signed by another key, or re-labelled with another owner fails. `scripts/policy-signoff.py keygen` makes a key pair (keep the private half with the owner only) and `sign` prints a rule with its `signoff` ready to paste. Keys are public and live in the binding, so they can be protected separately from the policy file; the check runs where the workspace is compiled, so that step must run in a place the workspace's editors cannot change. Custody of the private key and who may edit the binding remain the client's to arrange. The v1 Policy schema now accepts only a bounded, standard-base64 Ed25519 `signoff.signature` (64 raw bytes); the compiler still verifies it against the trusted environment owner key. A schema-valid signature is **not** authorization on its own. Legacy digest-only sign-offs remain syntactically valid but cannot relax approvals when `governance.ownerKeys` is configured.

**Ledger.** Every decision records the deciding rule ID as `policyRuleId` (or the built-in reason when no rule decided) and the rule-set version `policy:<digest>` as `policyVersion`. `govern-action.py`'s `record_policy_change(path, before, after, changed_by=...)` appends a chained `policy-change` event with the author and the rule-level diff, flagging rules that loosen control. The governed sidecar now calls it as it starts (`platform/core/policy_deploy.py`, `ledger_policy_deployment`): it compares the Policy rules in the compiled desired state it was deployed with against the rules it last applied (a private `policy-applied.json` beside the ledger) and appends one `policy-change` event when they differ, before it serves any request; an unchanged restart records nothing, and if the ledger cannot be written the sidecar does not start. The first start with no earlier record counts every current rule as added, so the trail begins with the rules the runtime started with. The identity recorded is `MODEL_GARDEN_DEPLOYED_BY` when the deploy sets it (a named person or workflow) and `runtime:deployment` otherwise; it is asserted by whoever runs the deploy and is not authenticated, so it names the person in the trail without proving who they are.

**Preview.** `python3 scripts/compile-workspace.py <workspace> --approvals` prints, per Skill, which Tool actions run automatically, need approval or are denied for members and for public callers.

**Bounded conditions.** An `allow` rule may carry `conditions` that can only *narrow* it (`conditions` on any other effect is a compile error):

```yaml
- id: faq-replies
  effect: allow
  actions: [mail.send]
  conditions:
    arguments: {category: [faq]}   # every named Tool argument must be present and equal to a listed value
    maxPerDay: 20                  # applies only while fewer than 20 successful executions of the matched Tool by this Agent are in today's (UTC) local ledger
    maxPerPrincipalPerDay: 3       # and only while the requesting person has fewer than 3 of them today, so one caller cannot use up everyone's allowance
  signoff: {owner: owner@client.example, ruleDigest: <sha256>}
```

When a condition is unmet, or cannot be checked (a missing or non-scalar argument, no readable or **chain-invalid** ledger), the rule does not apply and the stricter default stands, so a limited rule reached its limit shows `policy-limit-reached` with the rule ID in the ledger and the call needs approval. Values are compared by type (`1` does not match `true`). The conditions are part of the rule content, so editing them invalidates the owner's sign-off until it is re-signed. `--approvals` shows such a Tool as `conditional`. `maxPerDay` counts only this Agent's executions (a shared ledger no longer lets another Agent ration this one; events that name no Agent still count). `maxPerPrincipalPerDay` counts the requester's own executions and fails closed when the call names no requester, so an unattributed call never gets a per-person rule. A new public sender identity starts with a fresh count, so keep `maxPerDay` as the backstop for public rules; a public sender past their allowance falls back to the principal floor and is refused rather than queued. Counts come from the sidecar's local chained ledger; they are not a distributed rate limiter (concurrent calls can overshoot by the number in flight) and a client who deletes the ledger resets them, so use `deny`/`human-only` for hard limits.

**Daily-limit integrity boundary.** The counter verifies the full chained Action Ledger on the same shared-locked file descriptor before counting successful executions; a malformed record, broken hash/sequence, unexpected file replacement or unreadable ledger makes a limited `allow` rule inapplicable (approval remains required). For conditional daily limits, the executing governed boundary also holds a private, no-follow `<ledger>.quota.lock` advisory lock across policy re-evaluation, provider execution and the durable success/failure receipt. Two cooperating workers sharing the same trusted local governance volume therefore cannot spend the same remaining automatic allowance; an unsafe or replaced lock fails closed. Standalone `authorize_action` is a preview, **not** a quota reservation, and callers must use `execute_action` for effects. This remains host-local cooperative serialization, **not** a distributed/provider-side limit, independent ledger truncation anchor, or cancellation of a provider write after a crash. A crash after an external success but before the receipt may leave the allowance undercounted; an absent/empty legacy ledger still counts as zero. Use `deny`/`human-only` for absolute limits and retain live concurrent-provider and independent export proof as separate go-live gates (#80/#114).

Not yet supported: classification of free-text content (for example deciding that a message *is* an FAQ), verifying that the named owner really signed (a sign-off proves content integrity, not identity), and consultant/owner role separation beyond the sign-off above.

## Delegation between Agents (task envelopes)

`platform/core/delegation.py` holds the rules for a coordinator Agent handing work to a specialist without creating a way to do more than a person could have asked for. It is a pure module with tests; `platform/runtime/team_runtime.py` applies it to several Agents (see "Team of Agents"). In a team the model can hand work to a colleague through the delegation Tools (see "Delegation the way colleagues do it" under the team runtime); the Agent it names is checked against the team, and every limit here still applies.

- **Envelope.** goal, constraints, deadline, budget (`tokens`, `costCents`, `steps`), the Tools the task may use, the originating principal, the parent task and the chain of Agents so far. The root envelope's authority is the requesting person's permissions narrowed to what the first Agent holds; a child cannot change the originating principal.
- **Attenuation.** A delegate's effective authority is its own grants ∩ the delegator's authority for this task ∩ the originating principal's permissions, re-checked on every hop. A delegate asked to use a Tool outside that set is refused rather than silently narrowed, and authority never grows along a chain.
- **Bounds.** Depth (default 3), fan-out (default 5) and loops (an Agent already in the chain) are refused; a child's budget and deadline can only be tighter than what the parent has left, and a parent whose budget is exhausted cannot delegate (a task with an exhausted bound must halt and its owner be told, which nothing sends yet).
- **Governance and ledger.** `governance_context` yields the `originatingPrincipal`, `taskId` and `delegationChain` fields the governed boundary already binds into every `requestId`; `permits` is the check a runtime must make before policy evaluation; `record_hop` ledgers each hop as a `delegation.hop` event holding identifiers, counts and a digest of the goal, never the goal.

`scheduler.py`'s `BudgetMeter` halts a run that charges past its budget, ledgers `task.budget-exhausted` and notifies the owner (see "Running scheduled and triggered tasks").

### One budget across a delegated task tree

`delegation.delegate` bounds a child by what its parent has left, but alone it would let siblings each take all of it. `platform/core/task_budget.py` (`TaskBudgetTree`) makes the budget real across hops (#96). It is pure and credential-free; `platform/runtime/team_runtime.py` wires it to a team's governed calls (see "Team of Agents").

- **Delegating reserves.** A parent's available budget is `budget - used - reserved`; each child's budget is reserved from it, so children of a task can never add up to more than it had. A child delegated without a stated budget for a key takes everything left for that key, so state the budget for every key to share it.
- **Charged where it happens, counted once.** Usage lands on the task that did the work; when a child finishes or halts its reservation is released and what it used is rolled into its parent, so `total_spent` is the cost of the whole tree.
- **Exhaustion halts the task and its descendants and tells the owner once.** Charging past a task's available budget records the overspend, ledgers `task.budget-exhausted` (task, chain, exceeded keys, budget, spend; never the goal), halts the task and everything under it, and notifies the originating principal (`task-budget-exhausted`). A sibling branch keeps running (what to do about a failed branch is #98's policy), but a branch whose overspend pushes its parent over halts the parent too. Spending exactly the budget is allowed. `timeline` shows state, budget, spend, reserved and available per branch, and `snapshot`/`restore` round-trip the tree.

An in-process team runtime now enforces these budgets and delegation/human steps (#95–#97). Open: runtime-native handoff or A2A selection, parallel task graphs (#98) and real multi-Agent deployment evidence (#71).

## Coworker memory

`platform/core/memory.py` provides credential-free, scoped coworker memory. The governed sidecar exposes member-scoped memory Tools to the channel runtime (see [channels](channels.md)); integration with a replaceable runtime's own native memory remains undecided.

- **Scopes:** `client`, `agent:<name>` and `conversation:<id>`. A reader names the scopes it may see; anything else is invisible, so one conversation's memory never reaches another. A store belongs to one tenant, in its own file, and refuses another tenant's file.
- **Writes** redact card numbers, refuse `restricted` classification unless the deployment's policy allows it, are bounded (500 characters, 2,000 entries) and are idempotent per scope. Each write, delete, export and purge calls the audit hook with identifiers and a digest of the text, never the text.
- **People and administrators.** A person may list and delete entries they own; an administrator may export and purge per scope or for the whole client: `client-operator.py memory list|export|delete|purge --project-name <env>` (client data, so run it on the client host; the actor is as asserted on the command line, like approvals).

## Scheduled coworker tasks

`platform/core/schedules.py` is the contract for recurring work with a named owner ("send me a pipeline summary every Monday"). It is a credential-free store and cron arithmetic with tests, **not a scheduler**: nothing here wakes a coworker (the runner is `platform/core/scheduler.py`, below); chat commands are in `schedule_commands.py` (below) (#99). It also holds **event triggers**: an entry with an event kind (`mail.received`, `ticket.created` or `chat.message`) instead of a cron, with the same owner, budget and owner-only controls, a per-hour run limit (default 6, at most 60) and a digest of each handled event reference so an event never runs a trigger twice. `claim_due` and `claim_event` take a slot or an event atomically under the store's lock, `mark_outcome` counts consecutive failures (three suspend a schedule with `pausedReason: repeated-failures`) and a bounded, durable record of each run is kept for the runner.

- **Named owner and budget.** Every schedule belongs to one principal and must carry a per-run budget (`tokens`, `costCents` and/or `steps`, each at least 1). A run's task envelope comes from `delegation.root_envelope` with the owner as the originating principal, so its authority is the Agent's grants narrowed to the owner's permissions *at run time*; when the owner loses a permission the next run is refused (`ScheduleError`) instead of widened.
- **Cron-like, UTC.** Five fields with `*`, lists, ranges and `/step`; when both day fields are restricted either may match, as in standard cron. Fires closer than 15 minutes apart are refused. After downtime a schedule fires once for the slots it missed, and resuming after a pause never replays old slots.
- **Owner-only control.** Only the owner or an administrator pauses, resumes or deletes a schedule; at most 20 schedules per owner and 500 per tenant. One private file per tenant (another tenant's file is refused). Every change calls the audit hook with identifiers, the budget and a digest of the goal, never the goal.

### Running scheduled and triggered tasks

`platform/core/scheduler.py` makes each firing a task. It is credential-free and calls no provider (the coworker is an injected `runner`), and the runtime worker (`platform/runtime/worker.py`, see [self-hosting](self-hosting.md#runtime-worker)) calls `run_due` and `resume_waiting` on its clock with the coworker as the runner, and `run_event` for the events it witnesses: after the support mailbox handles an inbound message the worker fires `mail.received` (not for loops, spam or a redelivery, and once per message however often it arrives), and `ticket.created` when that handling opened a new Tier 0 ticket (#99, #109, #77). The runner is given only the event kind and a digest of the reference, never the sender, subject or text; a trigger at its hourly limit or already run for the event is skipped, and a failing run is ledgered as `worker.event-failed` with the error type only and never loses the mail. The worker's `events` job (every 30 s, `intervals.events`) covers the sources it does not witness itself. `ticket.created` fires for every Tier 0 ticket created since the job's last pass by any route (the coworker through the sidecar, a person, the mailbox), found with `TicketStore.created_since` (ids and times only); the first pass starts at the worker's own start so existing tickets are not replayed, and a ticket the mailbox already announced is skipped by the per-event reference check. `chat.message` fires for each conversational message the channel gateway reported: after a verified, first-time inbound message that is not a hand-off reply, schedule command or inbox command, `ChannelIngress` calls its `observed` hook and the gateway appends `{kind, ref, at}` to the shared `EventOutbox` (`platform/core/event_outbox.py`: `<data>/events/events.jsonl`, 0600, append-only, bounded to 1 MiB so an absent worker cannot fill the volume, with `ref` a digest of channel, conversation and message ids, never a sender, id or text). A full outbox drops the event and ledgers `channel.event-dropped`; the message is still answered. With no coworker configured the job leaves the outbox untouched. Any chat message in any conversation the gateway serves can run a `chat.message` trigger, bounded by that trigger's hourly limit, budget and owner permissions; there is no per-channel filter yet.

- **A task with a timeline.** A run is `<schedule id>:run-<n>`; it writes `task.start` and `task.finish` ledger events (identifiers, the goal's digest, budget, spend and outcome; never the goal, an event body or an error message) plus the human-step events below, and `timeline` reads one task's events back in order. Authority is built with `run_envelope` from the owner's *current* permissions, so an owner who lost a permission stops the run (`authority-refused`). An event reaches the runner only as its kind and a digest of its reference: it is data, never authority.
- **At most once.** The slot or event is claimed before the run starts, so two schedulers never run the same one and a restart never repeats it. A process that dies mid-run leaves the run `running` in the store (visible, not silently retried): a repeated side effect is worse than a late run. Events the coworker itself produced (`self_originated`) never trigger.
- **Budget halts and tells the owner.** The runner receives a `BudgetMeter`; charging past the per-run budget raises `BudgetExhausted` after recording the overspend, the run ends `failed` (`budget-exhausted`), `task.budget-exhausted` is ledgered and the owner gets a notice. Usage the runner reports at the end is charged the same way; spending exactly the budget is allowed.
- **Failures notify, repeated ones suspend.** A refused authority, runner error or exhausted budget produces one owner notice (`{key, kind, to, scheduleId, taskId, reason, text}` with no goal or error text, delivered through an injected `notify`; a failed delivery is returned as `delivered: false`, never lost) and counts toward three consecutive failures, after which the schedule is paused with a `schedule-suspended` notice.
- **Pausing on a person.** A runner may return `{"status": "waiting", "step", "assignee", "ask", ...}`; the run opens a durable Tier 4 hand-off (`human_step.py`) and ends the call. `resume_waiting` reads each waiting run's hand-off: the person's answer resumes the runner with their identity and note (data only; the envelope's authority does not change), a decline or timeout follows the fallback (`fail`, `skip`, or `escalate` once to a named person), a timed-out hand-off is closed so it does not linger in the inbox, and the opening, the person's answer and a timeout are ledgered in the task's timeline (the note only as a digest).

### Owner chat commands and workspace-managed schedules

`platform/core/schedule_commands.py` is the command layer a channel calls with the principal it verified (#99). One explicit syntax, no natural-language parsing: `schedules`; `schedule create <cron> | <budget> | <goal>`; `trigger create <event> | <budget> | <goal>`; `schedule pause|resume|delete <id>`. Anything else returns `None` and goes to the coworker. The owner is always the verified sender (the message cannot name another), the goal after the last `|` is data and never re-parsed as a command, an unverified sender gets nothing, and another person's id gets the same answer as an id that does not exist. Creating a schedule grants nothing: every run is still narrowed to the owner's permissions when it runs. It is not wired to a channel.

`ScheduleStore.reconcile` makes the store match a list of named definitions (`name`, `owner`, `agent`, `goal`, `cron` or `event`, `budget`, optional `requiredCapabilities` and `maxPerHour`), the client's desired state kept next to the workspace: a missing one is created, a changed one is updated in place (same id, same run history, an owner's own pause is kept), and a managed one no longer listed is **paused** with `pausedReason: removed-from-workspace`, never deleted, and comes back if listed again. Schedules made from chat are not managed and are never touched. Nothing is applied unless every definition is valid; a timed schedule cannot silently become an event trigger. `export_desired` writes the managed schedules back in the same shape. Changes are ledgered (`schedule.create`, `schedule.update`, `schedule.retire`) as identifiers and digests with who made them. A managed schedule an owner deletes is recreated by the next reconcile; the workspace wins. There is no workspace compiler or CLI step for this yet.

**Schedules in the workspace.** A `Schedule` resource (`contracts/v1/schedule.schema.json`, kept under the client workspace, for example `schedules/monday-summary.yaml`) is the file format for those definitions: `metadata.name` is the managed name and `spec` holds `agent`, `owner` (the named principal whose current permissions bound every run), `goal`, exactly one of `cron` or `event`, optional `maxPerHour`, a required `budget` and optional `requiredCapabilities`. The compiler validates it by schema and by the store's own rules (unknown keys, the 15-minute floor, a cron that never fires, a budget), refuses one that names an Agent the workspace does not define or Tools that Agent does not select, and adds the Agent's definitions to its compiled desired state as `schedules` (only when it has any, so a workspace without them compiles exactly as before). `compile-workspace.py --schedules` prints the definitions as JSON. On a runtime, `runtime-schedules.py <store> plan|apply|export` reads them from a JSON file or the compiled desired state: `plan` (`ScheduleStore.plan`, a dry run of `reconcile`) shows what would be created, updated, retired or left alone and changes nothing; `apply --by <person>` reconciles and ledgers the change under that person; `export` round-trips. The person named by `--by` is asserted on the command line, like approvals. A resource grants nothing: each run is still narrowed to the owner's permissions when it fires.

Open: delivery of owner notices and human steps to the person's own channel (`notice_delivery.py` is the runner; no real channel), a per-channel filter for `chat.message` triggers, a clock wired to the sidecar, a runner backed by the governed boundary and live evidence (#99, #96, #97, #73).

## Human step in a task

`platform/core/human_step.py` lets a task step target a named person using the Tier 4 hand-off store, with no storage of its own: the pending hand-off is the durable pause, so a restart loses nothing, and the inbox, notices and `runtime-handoff.py complete` are how the person is told and answers. `team_runtime.open_human_step` / `human_step` run it on a delegated task (see "Team of Agents") (#97).

- **The step carries the exact ask** and a short context; notices carry only the Tool name and a reference, never the ask.
- **`resolution`** reports `waiting`, `resumed` (done, with the person's note and identity), `declined`, `timed-out` or `unknown`. A decline or timeout never resumes: it returns the configured fallback (`fail`, `skip` or `escalate` to a named person). Reopening the same step returns the same hand-off and does not reset its clock.
- **No widening.** The answer is data for the task; it never changes the envelope's authority.
- **Ledger.** `task.human-step.opened` (under the Agent), `task.human-step.resolved` (under the person) and `task.human-step.timed-out` (under the task) hold identifiers, the outcome, lateness and digests of the ask and note.

`scheduler.py` is the first runner that pauses a task on this step and resumes it (see "Running scheduled and triggered tasks"). Open: delivery to the person's own channel and acknowledgement from it, a multi-Agent runtime that uses it, and live evidence (#97, #88).

## CRM sync states

`platform/core/crm_sync.py` is a provider-neutral delivery ledger for filing interactions to a CRM; it contains no provider code and does not call one (#115).

- **Key.** A stable idempotency key from tenant, channel, external call or message id and interaction type, so a redelivered webhook, a retry and a restarted worker reach the same entry and never create a second record; a provider that supports idempotent writes is given the same key.
- **States.** `pending`, `synced`, `failed`, `blocked`, `reconciled`. `synced` and `reconciled` need the provider's reference, so nothing claims a filing the provider did not acknowledge. Transient errors (`rate-limited`, `outage`) retry after 30 s, doubling to 1 h; `rejected`, `unauthorized` or eight attempts block until a named person retries. `reconcile` links a record found at the provider without writing it again.
- **Readable.** `describe` returns the state, the provider reference when there is one, and a plain repair action; transitions are ledgered with the key, state, attempt count and error code, never interaction content.

Open: cross-channel conversation timelines, verified identity linkage, wiring into the voice and email filing paths and connectors, safe provider swap with a re-link plan, retention/erasure across providers and live evidence (#115, #108).

## Deliverables and the Tier 0 artifact store

`platform/core/deliverables.py` builds real DOCX, XLSX, PPTX and PDF files (and CSV) from structured Agent output with the standard library only, and `platform/core/artifacts.py` is the Tier 0 store they land in when the client has no file system bound. Both are credential-free modules with tests; the builders and the store are behind the Tier 0 `docs.create` on the governed sidecar (`format` and `structure`; see Tier 0 document store), but they are not driven by a Skill and are not behind `files.write` (#101, #77). The channel gateway posts a deliverable the requester's own coworker kept back to them: as a reference line on every channel and, for Slack with `slack.upload_files`, as an uploaded file (see `docs/channels.md`, Slack).

- **Builders.** A report (DOCX or PDF) is a title plus sections of headings and paragraphs; a workbook is sheets of rows; a deck is a title slide plus slides of a title and bullets (text only, 16:9). Output is deterministic (same input, same bytes and digest). Spreadsheet strings are written as literal inline strings and CSV cells that start with `= + - @` are quoted, so text from an email cannot run as a formula; XML is escaped and control characters removed; sizes are bounded. The PPTX holds only text shapes and the PDF only text operators (Helvetica, A4, wrapped and paginated, non-Latin-1 characters become `?`): no hyperlinks, actions, JavaScript, embedded files or macros, and no dates or producer, so output stays deterministic. Tests parse the package and the PDF cross-reference table; the files were also opened in LibreOffice and poppler once by hand, which is not evidence from PowerPoint, Word or a client's PDF reader. Native Google/Microsoft formats are not generated.
- **Store.** One directory per tenant (0700, files 0600, an index for another tenant is refused). Files are named by artifact id, never by the display name. Only office, PDF, CSV, Markdown and text types, at most 10 MB and 2,000 artifacts; `restricted` data is refused unless the deployment's policy allows it. A read recomputes the SHA-256 and refuses a file that changed on disk.
- **Accountable.** Each artifact records who asked, which Agent produced it, a bounded list of source identifiers (for example `kb:rules-of-engagement#hours`) and its `tier0:<tenant>/<id>` location. `artifact.create`, `artifact.read`, `artifact.delete` and `artifact.expire` are ledgered with identifiers, size, digest and sources, never content or names.
- **People and retention.** The requester or an administrator reads or deletes; artifacts expire after the client's retention period (default 365 days) and `purge_expired` removes the files. `client-operator.py artifacts list|delete|purge-expired --project-name <env>` is the operator view (client data: run it on the client host; the actor is as asserted on the command line, like approvals).

Open: native Google/Microsoft formats, charts/images/styling, binary `files.write`, Teams file upload, Skill-driven generation, evals through the runtime and live evidence (#101, #77).

## Skillsets

`platform/core/skillsets.py` is the credential-free first contract for reusable Skill bundles. A Skillset is a versioned list of Skill **references**, not a security principal, an Agent, an all-or-nothing unit or a place for credentials. It is **not yet read by `compile-workspace.py` or a registry**; it produces the `skills` and `disabledSkills` values the compiler already understands (#128).

- **Validation** is strict: unknown keys are refused, and so is any key that looks like a secret (token, password, API key, credential).
- **Expansion is deterministic and fails closed.** Direct Skills, selected Skillsets and `includes` expand to one sorted, deduplicated list with the sources that brought each Skill. A missing Skillset or Skill, a pin that differs from the available version, conflicting pins, a cycle or nesting deeper than 4, and an include with several versions each raise an error and expand nothing.
- **Selection is not activation.** `activation` gives every selected Skill a coworker-specific state, all off unless named; `exposed_tools` returns Tools only through enabled Skills, so enabling one member never adds another member's Tools. The compiler's own readiness still blocks an enabled Skill whose dependency is missing.
- **Independent per coworker.** The same bundle resolves against each coworker's own available Skills and enabled set; the bundle holds no coworker state.

Open: reading Skillsets in the compiler or a registry, knowledge-aware prerequisites, per-coworker identities and grants (#129, #95), runtime re-evaluation at invocation, the reviewed PR → DEV/evals → business approval → PROD change flow with rollback, and live evidence (#128).

## Per-coworker provider grants

`platform/core/provider_grants.py` defines per-coworker authorization to a connected system (#129). It holds **references**, never secret values. The governed upstream MCP/API path checks the coworker's connection-specific grant, selected Tool scopes, status and runtime-attested Agent identity before dispatch, alongside the environment's provider/capability selection. Offline tests cover isolation and failure paths; they do **not** prove independently authenticated acting identities or revocation in a real source-provider tenant.

- **One grant per coworker and connection:** immutable tenant (client and environment), Agent, family, provider and connection id, the provider-side acting identity or isolated delegated grant, a `secret://` reference, granted Tools, an owner, health, optional expiry and a revocation state. Operators see the reference only as a digest.
- **No shared credentials.** A secret reference or acting identity held by another coworker is refused, as is a `shared-login` grant next to a second coworker on the same family (a shared login is allowed for a lone coworker but reported `multiCoworkerSupported: false`).
- **Attested caller only.** `resolve` takes the runtime-attested Agent name and no argument through which a model, coordinator or delegate could name another coworker or hand over a token. Rights are the originating principal's permissions ∩ the coworker's granted scopes ∩ the Tools enabled for it; revoked, expired or failed grants refuse instead of falling back.
- **Independent lifecycle and secure upgrade.** Revoking, rotating or degrading one grant never changes another. `upgrade_from_environment` proposes a grant from an environment binding only for a workspace with exactly one Agent and refuses several, so an old shared token is never silently reused. `receipt_fields` gives the attribution a call must carry (Agent, initiating principal, grant, connection, provider-side identity, scopes, request id).

`revoke_all` offboards one coworker (or the whole tenant) in one step, ledgering each revoked grant and returning the secret references the person offboarding must delete; see "Per-coworker offboarding" in the governed Tools document. Open: independently provisioned real-provider acting identities/grants, verification against provider-side audit/revocation and real-tenant proof for each advertised authentication mode (#129, #110, #86).

## Team of Agents

`platform/core/team.py` checks the compiled desired states of several Agents (the compiler already emits them when no `--agent` is given) before a runtime may advertise more than one coworker. It changes nothing itself; `platform/runtime/team_runtime.py` (below) is what refuses to start a team that fails it. `deploy-team-docker.py` renders the Docker bundle that runs one sidecar per Agent (#95).

- **Tool isolation.** `authorize_call` allows a call only if the Tool is one of the *calling* Agent's own compiled Tools, using the attested Agent name; another Agent's Tool is refused. The action request identity already includes the Agent, so one Agent's approval cannot be replayed by another.
- **Own provider access.** With several Agents, each Agent whose Tools belong to an external (tier 1+) family needs a usable grant of its own covering them (`plan` reports `blocked` with a plain reason); Tier 0 families need none; an unbound family blocks. Duplicate Agent names are refused.
- **Single-Agent workspaces are unchanged:** one Agent and no registry is `ready` through the environment binding.

**Team runtime (`platform/runtime/team_runtime.py`, `scripts/runtime-team.py prepare compiled.json --base DIR --environment-binding env.yaml`).** One governed runtime per Agent, so the Agent is the runtime instance a call reaches and never something the model says:

**Delegation the way colleagues do it** (`platform/core/task_inbox.py`, `TeamRuntime.assign_task` / `delegate_task` / `report_task`; #95, #96, #98). Work moves between Agents and people as it does between colleagues: it is handed over, it waits in the colleague's inbox, and they finish it, decline it or say it failed, and the one who handed it over reads the answer.
- **A person can hand a task to any Agent** with `assign_task(person, agent, ...)`. The person is whoever the host verified; their permissions come from the host (`permissions_for`). The Agent works only with the Tools it holds that the person may ask for, so a person cannot get more done through an Agent than they could ask for; if nothing is in common the assignment is refused and ledgered (`task.assign-refused`). The person reads the Agent's report with `task_result`, and nobody else can (an unknown task and someone else's task give the same answer).
- **An Agent can hand part of its own task to a colleague** with `delegate_task` (or the `delegate_task` Tool). The parent must be an open task in that Agent's own inbox, and its authority and budget come from what the team stored, not from the caller. All the existing limits apply: the colleague's own Tools, no widening, no loops, bounded depth and fan-out, and the child's budget reserved from the parent's. The colleague finds the task in their inbox (`my_tasks`), and an Agent may not finish a task while a colleague it asked has not reported.
- **A colleague can say no.** `report_task` ends a task as `done`, `declined` (with a reason) or `failed`, returns its unused budget to the parent and tells the one who asked. The report is bounded text and is data, never instructions; the ledger holds its length and digest (`task.reported`), not the text, so the task timeline shows who handed what to whom and how it ended without any personal data.
- **Tools.** When a team has more than one Agent each sidecar offers `team_directory`, `my_tasks`, `delegate_task`, `report_task` and `delegated_task_status`. Each Agent acts only as itself on its own inbox; a refusal comes back as `refused` and a bad request as `invalid`, with the reason.
- **A person assigns from the command line.** `python3 scripts/runtime-team.py assign compiled.json --base DIR --environment-binding env.yaml --owners owners.json --person NAME --agent AGENT --goal "..."` hands a task to any Agent (`--owners` is `{person: [Tool names]}` or a worker config with `owners`; `--capability` and `--budget-steps|tokens|cost-cents` narrow it). It saves the task and the inbox entry under `--base`, and the process that runs the Agents finds it without a restart (it loads task trees it does not hold yet when asked about an unknown task; it never replaces one it already holds). `inbox --agent` shows what is waiting and `result --person --task` shows the report to that person only. On the host the person is as asserted, like the other operator commands.
- **A person assigns from a chat message.** `assign <agent>: <goal>` (or `delegate`) in a direct message hands a task to a team Agent under the speaker's own identity. `ChannelIngress` takes an injected `assign(person, agent, goal)` callable that is expected to call `TeamRuntime.assign_task`; a refusal (`ValueError`) is shown without the goal, a stranger or a shared channel gets one fixed answer, and the ledger notes `channel.task-assigned` with the agent and the goal's length only. When no callable is wired the words are an ordinary question.
- **Limits.** Each task tree is changed only by the process that runs the Agents (the command only starts new trees and reads), so sidecars launched as separate containers still do not share task state; the inbox is saved to `inbox.json` and is safe across processes. The gateway does not yet build a `TeamRuntime`, so the chat command is parsed and routed but no deployed gateway wires `assign` to it; nothing runs the Agent when a task arrives (the host or the Agent's own conversation takes it up from `my_tasks`), and none of this has live evidence.

- **Isolated state, one ledger.** Each Agent has its own approval, hand-off, memory and artifact roots under `<base>/agents/<name>/`, its own desired state and capability manifest, and every Agent appends to the one hash-chained ledger at `<base>/audit.jsonl` with its name on each event. A pending approval, hand-off or file of one Agent is never visible to another; the per-Agent usage counts (`maxPerDay`, `maxPerPrincipalPerDay`) and the operator `audit` filters work on the shared ledger. Policy and knowledge changes are ledgered per Agent (`team.ledger_deployments`, `--ledger-deployments PERSON`).
- **Refuses to start unready.** More than one Agent starts only when `team.plan` is ready: each Agent that needs an external connector family holds a usable grant of its own (never a shared login), no family is unbound, names are unique lowercase DNS-like names (they become directories). Otherwise it raises (the CLI exits 1) naming every blocker and writes nothing. One Agent starts exactly as before.
- **One sidecar per Agent.** `launch_plan` (printed by `prepare`) gives each Agent its own `governed_mcp.py` command, port, approval root and manifest, sharing only the ledger. An Agent's Hermes profile points at its own port; no routing by a model-supplied name exists.
- **Delegation under the envelope rules.** `start_task` and `delegate` apply the rules above with the delegate's own compiled Tools as its grants and the parent's authority as the originator bound (it can only shrink). Each hop is a `delegation.hop` event and each refused hop a `delegation.refused` event naming the refusal reason; fan-out is counted from the saved task tree, so it survives a restart. A governed call made under `team.acting(agent, envelope)` carries `taskId`, `originatingPrincipal` and `delegationChain` in the ledger's governance context, and is denied and ledgered (`outside-delegated-authority`, `task-deadline-passed`, `task-budget-exhausted`, `task-bound-to-another-agent`) before policy is consulted when it is outside the task's authority, past its deadline, out of budget or running on another Agent's runtime. An envelope that does not belong to the Agent or names a Tool it was not compiled with is refused.

- **One budget per task tree, charged as calls happen.** `start_task` begins a `TaskBudgetTree`, saved under `<base>/tasks/` after every change so a restart resets neither spending nor fan-out; `delegate` reserves the child's budget from its parent. Every governed call under a task is charged one `steps` before it runs; `team.charge(envelope, tokens=…, costCents=…)` adds what the host measured. Past a budget the call is refused (`task-budget-exhausted`), `task.budget-exhausted` is ledgered, the branch and its descendants halt, and the originating principal is told once through the host's `notify` (the worker passes its notice queue). `finish_task` releases an unused reservation; `task_status` shows each branch's spend and what is left. An envelope the team did not start, or one whose principal, chain or authority differs from the stored task, is refused.
- **A person as a task step.** `open_human_step(envelope, step=, assignee=, ask=, timeout_hours=, fallback=fail|skip|escalate)` opens a Tier 4 hand-off on that Agent's own store (so the existing inbox, notices and channel reply reach the person) and `human_step(envelope, step)` reports `waiting`, `resumed`, `declined` or `timed-out` with the configured next step. The opening, the person's answer (under their name, with a digest of the note) and a timeout are each ledgered once, and the answer never widens the task's authority.
- **Parallel branches under one budget (#98).** `team.fan_out(parent, branches, runner=, policy="fail-fast"|"best-effort", max_concurrency=)` delegates several independent sub-tasks of one task (each reserves its share of the parent's budget, so branches together never spend more than the parent had), runs `runner(agent, envelope, runtime)` for each on a bounded pool under that branch's own envelope, and joins. Each branch ends `succeeded`, `failed`, `budget-exhausted`, `refused` (the hop itself was refused, ledgered as `delegation.refused`) or `cancelled`; `fail-fast` starts no further branch after the first failure or refusal (a branch already running finishes), `best-effort` runs every branch it could delegate. Concurrency is the smaller of the call's `max_concurrency` and the environment's `max_parallel` (default 4, at most 32), a limit shared by every fan-out. The fan-out (`task.fan-out`), each branch (`task.branch.finished`: Agent, outcome and its tokens, cost and steps) and the join (`task.join`: counts by outcome) are ledgered against the parent task and show in `audit timeline --task`; a branch's error is recorded by type only and its value is returned to the host, never ledgered. Like the rest of the team's task state this runs in one host process: a model cannot start a fan-out yet, and nothing here is live evidence.
- **The task timeline sees all of it.** `audit timeline --task T` now includes the operator events that name the task in their details: delegation hops (from either end), refused hops, human-step events and an exhausted budget, each with who, the identifying fields and no goal or note text.

The task state and the budget live in one host process; sidecars started from `launch_plan` do not consult them.

Open: a worker that serves each Agent's hand-offs, the runtime-native handoff/A2A decision, task state shared across separately launched sidecars, a channel message for assigning a task, provisioning real per-coworker provider identities, and cross-Agent token isolation proof against a real provider (#95, #96, #97, #129).

### Deploying several Agents in one environment

`scripts/deploy-team-docker.py <profiles-root> <environment-binding.json> <bundle-dir> --project-name NAME` (or `--profile NAME=DIR` per Agent) renders one Compose bundle with a full runtime per Agent (#95), the Docker counterpart of `team_runtime.py`'s `launch_plan` (here each Agent also has its own ledger volume rather than one shared ledger). It is opt-in and credential-free: `deploy-client-docker.py` is untouched, so single-Agent bundles are byte-identical, and a team is 2 to 12 Agents.

- **One attested identity per Agent.** Each Agent keeps its own compiled profile; the sidecar attests the Agent from that profile's desired state `source.name`, which must equal the profile directory name and, when present, `EnvironmentBinding.spec.agents`. Duplicates and mismatches are refused. Each sidecar also gets its own initiating identity `runtime:hermes:<agent>` (single-Agent bundles keep `runtime:hermes`), so grants, MCP connections, approvals, hand-offs, memory and ledger events are attributed to the right Agent.
- **Nothing shared but the model credential reference.** Services are `<agent>-<service>`, state volumes (including the hash-chained ledger) are per Agent, and each Agent has a private network on which its services keep the usual short names, so profiles and worker config work unchanged and one Agent cannot reach another's sidecar.
- **`spec.agents`** is a list of names (checked against the profiles) or an object mapping an Agent to an overlay of binding keys (`gateway`, `worker`, `upstream_mcp`, ...) that replaces the shared key for that Agent only. Two Agents publishing the same host port are refused, so give the channel gateway to one Agent with an overlay.

## Governed MCP passthrough

`platform/core/mcp_passthrough.py` defines the narrow approved operation contract; the separate `platform/runtime/upstream_http.py` implements a pinned-address, bounded MCP transport behind the governed sidecar. Hermes sees only selected portable Tool names, never raw server URLs or arbitrary MCP methods (#87/#158).

- **Declaration.** Name, https URL (no credentials, query or fragment), `secret://` credential reference and an explicit allow-list; every allowed tool has an explicit risk class (`read`, `write`, `privileged`, `external-communication`) and may map to a portable capability Tool (for example `crm.read`). There is no allow-all; unclassified entries are refused.
- **Exposure.** Unlisted upstream tools are never exposed (they are only counted); a listed tool the server no longer offers is reported missing. Exposed tools become `modelgarden.ai/v1` Tool resources of type `mcp`, with `approvalRequired: true` for anything but `read` (a signed client policy can relax it, as for native Tools).
- **Schema pinning.** An operator approves a tool by fingerprint over its name, description and input schema. A changed definition (including a rewritten description) hides the tool and `call_gate` fails closed until it is approved again; approvals are ledgered as fingerprints, never schemas.
- **Ledger.** `ledger_fields` supplies `tier: 2`, `provider: mcp:<server>`, the server and upstream tool name, never arguments or results.

Operator-assisted private connection staging, review and activation, exact coworker grants, sealed owner credential enrollment and generic OAuth consent/refresh are implemented in code. **Open:** proven real-tenant provider connections, complete source-side identity/credential lifecycle, secure deployment acceptance and client self-service (#87/#89/#159/#86).

**Not yet shipped — customer self-service custom integration (#159).** Operator-assisted MCP/REST execution and owner-controlled secret enrollment exist, but there is no complete client-facing connection wizard or real-tenant acceptance. The [client target](https://modelgarden.atlassian.net/wiki/spaces/BA/pages/327715) requires permissioned endpoint and operation review, constrained egress/SSRF checks, secure vault-backed OAuth/API-key enrollment, tenant/coworker-grant isolation, runtime approval/ledger and revoke/rotate. #87 and #89 own execution mechanics, #158 the common gateway, #110 guided onboarding and #159 the client-defined MCP/API experience. No caller may expose arbitrary HTTP requests as a Model Garden Tool, and no secret should enter a prompt or client workspace.

### Customer-managed MCP and custom API safety contracts

The independent endpoint/operation validation groundwork merged from #165 is preserved: `platform/core/endpoint_guard.py` rejects private, local, metadata and malformed HTTPS destinations and requires DNS answer validation/pinning; `platform/core/mcp_tool_review.py` blocks obvious tool-description/schema poisoning prior to operator approval; `platform/core/custom_api.py` defines explicit, versioned OpenAPI/REST operations with path/body bounds, method-derived risk and schema review. `mcp_passthrough.py` integrates endpoint and metadata checks into approval/exposure. These are **platform governance contracts** without a bespoke customer-vendor API client or arbitrary URL requester. The separately implemented upstream MCP and custom REST transports run only reviewed operations through the governed sidecar (next section); live tenant evidence remains open.

### A client's own REST API through the governed sidecar (v0.8.31)

A customer-defined REST API (#159, #89) now runs through exactly the same governed path as an upstream MCP server, with no new store, approval or grant mechanism and no general HTTP Tool.

- **Declared as a connection.** An MCP connection declaration may carry an `api` part: a `custom_api` definition (base URL, authentication by `secret://` reference, explicit operations). `mcp_passthrough.validate_server` refuses it unless the two agree on every point: the definition's name is the server name, its base URL is the declared URL (so the address qualified and pinned is the one requests go to), it authenticates with the declared credential reference (`none` is refused), and the allow-list is exactly its operations at exactly their method-derived risk. Each operation must still map to a catalog Tool of the same risk to be staged (`crm.read` for a `GET`, for example).
- **Same lifecycle.** `McpConnectionStore` stages, takes owner consent, activates against the operations' approved fingerprints (`custom_api.operation_tools`, now plain JSON Schema of the arguments with `x-` annotations pinning method, path, base URL, risk, auth type and parameter location) and the coworker's own grant, disables and replaces it exactly as for MCP. The ledger names the provider `api:<name>`.
- **Same execution.** `mcp_executor.invoke` re-resolves grant and activation, qualifies and pins the base URL's address, validates arguments against the approved schema and rechecks just before sending. The transport is `upstream_http.RestApiSession`: it lists only the definition's operations and sends only the request `custom_api.build_request` builds for one approved operation to the pinned address, with the credential as a bearer token, a named API-key header or basic auth. Redirects, 401/403, 429 and 5xx are errors; another 4xx is an operation failure; a non-JSON or oversized reply is refused; nothing upstream is echoed and an opaque `id` becomes the external receipt.
- **Installed with upstream MCP.** `MODEL_GARDEN_UPSTREAM_MCP=enabled` installs the REST transport next to the MCP one; without it, or in a runtime built without it, an `api` connection is neither offered nor callable.

The operator's steps are commands in the governed sidecar container: `runtime-mcp-connections.py <store> --tenant <client-env>` `stage`, `review` (each declared operation as offered now, with fingerprint, approval state and blocking findings), `approve` (pins exactly what was reviewed; refused while any operation has unsafe metadata), `activate --owner-consent <owner>` (the declaration's named owner, a different person from the operator) and `test` (the pins still hold and, with `--operation`, one declared *read* runs through the governed executor; only a credential or transport failure marks the coworker's grant failed, a mistyped argument or an upstream error is just a failed test, and only the result size and receipt are printed). The same commands serve an MCP server, listing its tools through the pinned transport. Owner-entered credentials for these connections go through a single-use enrollment link to a sealed vault only the sidecar can open ([secrets](secrets.md#owner-entered-credentials-sealed-vault)). Still open: a client-facing page for adding and reviewing the API definition itself (operator-staged today), and live evidence against a real client API.

### One-time secret entry and public candidates

Two vendor-neutral, credential-free pieces for the upstream-only direction.

- **One-time owner secret entry (#159, #86).** `platform/core/secret_enrollment.py` opens a single-use enrollment for one coworker's connection and returns a token once (stored only as a digest, at most an hour, bound to the tenant, coworker, connection and the named owner). The owner's value goes straight to an injected vault (`put` and `delete` only, it can never read back) under a versioned `secret://` reference; the store, ledger, results and errors never contain it, and a status shows only set, version, who and when, an expiry health and a masked length. A rotation writes the new version first and deletes the old one only after; a vault that refuses changes nothing; `revoke` deletes and is not recorded as revoked until the vault says so. A wrong person, an expired, used, cancelled or guessed link is refused and ledgered without the token or the value.
- **Public registry candidates (#157).** `platform/core/connector_candidates.py` turns an official-registry-style listing into a candidate (provenance, source digest, vetting findings by code only: unsafe remote, unpinned version, package without a digest, unapproved licence, poisoned description or sample tools, wildcard or excessive scopes, stale listing, version conflict) and walks it `discovered → reviewed → contract-tested` with a named person and a contract-test digest. `approved`, `coworker-authorized` and `tenant-live-proven` cannot be set there: they are read from `contracts/v1/integrations.json`, the per-coworker grants and the evidence manifest, so `directory` shows a candidate next to the registry and is `providerReady` only when a linked registry entry is built or live. A new version or changed content resets a candidate to `discovered`, a deny-listed name stays denied across feeds, a failed or rate-limited feed keeps the last good snapshot and reports `stale` after a week, only exact operations the owner maps to a capability in the catalog are exposable (the rest are counted, and non-reads need approval), and a tenant's own custom connectors live in a separate private book that the public book refuses and vice versa.

The enrollment is served by the gateway's `/connections/enroll` page into the sealed vault ([secrets](secrets.md#owner-entered-credentials-sealed-vault)), and `scripts/connector-candidates.py refresh` fetches the official registry. Open: tenant RBAC over who may enroll, approve or promote, per-coworker identity provisioning (#129), and live evidence for any route.

## Approved upstream MCP activation contract (v0.8.4)

A deployed coworker no longer passes arbitrary MCP server definitions to the internal executor. `McpConnectionStore` is a private per-tenant activation registry: an operator **stages** an explicit, catalog-mapped and risk-matched declaration (disabled); the client owner **consents**; an operator **activates** only after upstream schema fingerprint approvals and the coworker's own matching provider grant exist. Connection IDs must match grants, and status survives restart. `disable` and `replace` make the connection unusable immediately; replacement needs renewed schema review and owner consent. Public status contains only connection ID, provider and digest, not a credential or reference.

Call-time resolution validates the compiled coworker, tenant/environment, selected Tool, provider, grant and activation digest; a changed tool schema or connection revision fails closed. Material approval identifiers include a digest of connection revision and grant to prevent cross-route approval reuse. The implementation has credential-free tests; live source transport, hosted owner enrollment/authentication, actual vault-backed secret input and customer proof **remain unimplemented**, so no external provider becomes live merely by staging an MCP connection.

## Upstream-only provider integrations (v0.8.0)

Model Garden does **not** implement or maintain vendor-specific REST clients. The former native Google/Microsoft Calendar, Gmail, Outlook, HubSpot, Salesforce and Google Drive modules and their dedicated transport/test helpers were retired in v0.8.0. The registry keeps those provider names **planned** with method `governed-mcp` and tier 2 so clients know the intended coverage; it does not claim that any external server is approved, connected or live.

- **Use maintained ecosystems instead of parallel connector implementations.** Discover candidates through the [official MCP Registry](https://registry.modelcontextprotocol.io/v0.1/servers?limit=100) and vendor-maintained catalogs. Do not create a second locally maintained catalog, sync job or OAuth client framework.
- **Reuse the existing governance boundary.** `platform/core/mcp_passthrough.py` already validates upstream HTTPS declarations, explicit Tool allow-lists, risk classifications, fingerprints and audit fields. It is **not** connected to live upstream execution; #158/#87 must wire one small governed MCP client via the standard SDK, per-coworker grant selection and owner OAuth, not duplicate this validation.

This release does not silently reuse previous OAuth tokens or substitute a shared administrator credential. The compiler and deployer block unsupported Calendar skills.

## Owner notices for connections and provider grants

`platform/core/connection_notices.py` works out who should be told when a connection or a per-coworker provider grant needs a person (#86). It sends nothing: a deployment delivers each notice through a channel or the inbox and then records it, as with hand-off notices. It is credential-free; the runtime worker delivers its notices through `notice_delivery.py`.

- **Conditions.** A capability connection that is `degraded`, `failed` or `revoked`, and a grant (#129) that is revoked, failed, degraded, expired or expiring within a warning window (default 7 days).
- **Who.** The connection's named `owner` from the EnvironmentBinding, or the grant's owner; with none, the escalation contact; with neither, the notice is still returned with `to: null` and `unowned: true`, so it cannot be silently dropped.
- **Once per state, at least once.** A notice has a stable key (connection or grant, condition, when the state began), is offered until delivery is recorded, and is not repeated for an unchanged state. A cleared condition is forgotten so a recurrence is told again. Only a notice the store offered can be marked delivered; `connection.notice-delivered` is ledgered with the key, kind and channel.
- **Non-secret.** Notices name the family or the grant's connection, the condition and a recovery step, never a reason string, scope, account, secret reference or the provider-side identity.
- **Told is not seen.** The notice's named recipient (or the escalation contact) can `NoticeStore.acknowledge` a delivered notice, ledgered as `connection.notice-acknowledged` with who and through which channel; nobody else can, and an undelivered or unknown key cannot be acknowledged. A delivered notice nobody acknowledges within the window (`acknowledge_within_seconds`, default 24 hours, at least 60 seconds) is offered once more as its own `<kind>-unacknowledged` notice to the escalation contact, and never when there is no contact or the owner already is the contact. An acknowledgement stops that escalation only: it does not mark the connection fixed. A cleared condition forgets both. No channel command reads an acknowledgement yet and nothing sends or schedules these notices.

### Delivering notices to the named person's channel

`platform/core/notice_delivery.py` is the credential-free runner between these notices (and the Tier 4 hand-off notices, which carry human task steps) and a channel (#88, #97, #86). A small people directory maps a named person to one channel and one address (for a chat channel, the id of the conversation with that person; the directory refuses credentials and unknown keys). Each channel is an injected `send(address, text)`; `adapter_sender` wraps a channel adapter's `send_reply`. It holds no credential; the runtime worker runs it on its clock.

- **The person's channel.** A person with no directory entry, or a channel with no registered sender, is reported `no-channel` and the notice stays due; `inbox` counts as a channel only when the person's entry says so, so a notice is never marked delivered because it was merely visible.
- **At least once.** Delivery is recorded after the send succeeds. A failed send records only the error type, leaves the notice due and does not stop the rest of the batch; a send whose recording then fails is reported `unmarked` and sent again next run rather than lost.
- **Unowned stays loud.** A notice with no recipient is reported `unowned` and ledgered every run.
- **Safe text.** Notices carry the Tool, deadline and reference, never the action's arguments. The ledger (`notice.delivered`, `notice.delivery-failed`, `notice.undeliverable`) records source, kind, reference, channel and error type, never the message text or the address.
- **Operator command.** `runtime-handoff.py <store> deliver --people people.json` runs it for hand-offs with the `inbox` channel only (it carries no transport); everyone else is reported `no-channel`.

Open: wiring this into the sidecar or a scheduler, real Slack, Teams and email transports, acknowledgement-based escalation, OAuth consent, token refresh and provider-side revocation (#86, #88, #97, #110).

## Cross-channel conversations and customer linkage

`platform/core/conversations.py` is the credential-free core of one coherent history across voice, email, chat and hand-off (#115). It is not a CRM and holds no message text. The call-filing command and the worker's support mailbox put finished conversations on it (below); chat and web chat do not yet.

- **Ids and references.** A conversation id (`cv-…`) is derived from the tenant, channel and the channel's own call or thread id, so redelivery and restarts reach the same one; an interaction's key comes from its kind and external id, so it is stored once. Interactions are *references* (`transcript:…`, `message:…`, a ledger `requestId`, a content digest, a short outcome label), never text, and carry the Agent, Agent version, task and trace ids. Late arrivals sort by when they happened, then by arrival.
- **Evidence, then a deliberate link.** Evidence (`email`, `phone`, `sso`, `name`) is kept as a digest of the normalised value with `verified` and a provenance; a name can never be verified. `resolve` asks an injected directory which customers hold each *verified* digest: exactly one makes a `CustomerLink`; two or more is `conflicting-evidence` and goes to the review queue; evidence that is only asserted but matches someone goes to the queue as `asserted-match` and never links itself; anything else stays unlinked. The state is not to be reflected to the caller. A named person confirms or dismisses a queued item and is ledgered.
- **One timeline per customer.** `customer_timeline` joins every conversation linked to a customer across channels in one ordered list; two different customers never share a timeline, and an unlinked conversation appears in none.
- **Private and erasable.** One file per tenant (0600 in a 0700 directory; another tenant's file is refused), customer erasure removes every linked conversation and its review items, conversations can be erased singly or purged by retention, and audit events hold identifiers only.

`platform/channels/conversation_recorder.py` is the thin recorder between the channels and this store (#115, #108, #109). `ConversationRecorder.record_call` puts a stored call transcript on the timeline by reference (transcript, outcome label, a transfer as a hand-off, each ledger request id as an action receipt and a digest of a *model* summary; an extractive summary stays in the transcript store) and `record_email` does the same for a handled inbound email (thread and message keyed by digests, since Message-IDs are not safe keys; the handling outcome; a hand-off when it went to a person). A caller number, if the caller passes one, is *asserted* evidence, so a voice conversation never links by itself and at most queues a match for a person; a sender the receiving server verified is *verified* evidence, and `contacts_directory` (built on `ContactStore.identities`, an internal read that is not a Tool) lets `resolve` link it when exactly one contact holds the address (two holders go to review). Everything is idempotent and best-effort: `file_call_transcripts(..., recorder=…)` and `SupportMailbox(..., conversations=…)` call it after filing or replying, log only an error type if it fails, and are unchanged without it. 

**Wired in (v0.8.28).** `runtime-file-calls.py` (`client-operator.py file-calls`) records each call it files, and the runtime worker's support mailbox records each email it handles, in a per-tenant store on the data volume (`/opt/data/.modelgarden/conversations`; the three runtime modules and the command are in the sidecar image). Linking uses the Tier 0 contact log when `crm` is bound to it, rebuilt on each lookup so a contact a person adds while the worker runs can match the next email; with no Tier 0 contact log, conversations are recorded and never linked. A call's number is not passed (the transcript does not hold it), so a call joins a customer only when a person links it. A recording problem is logged by type and never changes how a call was filed or an email answered; the file-calls summary reports `timeline: {recorded, failed, skipped}`.

`client-operator.py conversations stats|list|review|timeline|confirm|dismiss|link|unlink|erase|purge --project-name <env>` (`scripts/runtime-conversations.py` inside governed-tools) is the person's view: the review queue (reason and candidate customer ids), one conversation's or one customer's timeline (references and labels only, never a message, number or address), `confirm <rv-id> --customer <id> --by <person>` and `dismiss`, `list [--unlinked]` (ids, channel, start time, size and link state only), `link --conversation <cv-id> --customer <id> --by <person>` for a conversation the queue never held (a number-less call has no evidence to propose a match from; a conversation already linked to a different customer is refused until `unlink`), erasure of a customer's or one conversation's history and retention by age. Every change is ledgered under the named person; reading is not. Chat and web chat conversations are not recorded yet.

### Scenario A acceptance (#117)

`tests/test_scenario_a.py` is the zero-stack acceptance run: one compiled receptionist, only the built-in providers (approved text knowledge and the Tier 0 contact log), taking a voice call through `file-calls` and customer email through the runtime worker's mailbox. It checks that a verified customer's email lands on their timeline and a person can link the call to the same history (ledgered under their name); that answers are grounded in an approved section and only ever drafted for a person, never sent; that a question the rules do not answer goes to a person and nothing is invented; that an email giving orders (refund, create a contact, send the list) causes only a governed knowledge read and at most a draft; that an unverified sender is not treated as the customer; that redelivery and re-filing change nothing; that no card number, call words or email text reaches the ledger or the timeline; and that the audit chain is intact. It is credential-free and in-process: it is **not** Scenario B (no provider is connected), not a live deployment, and not evidence about any provider, so it does not by itself justify a go-live claim.

A sync-ledger entry can carry the `cv-…` id of its conversation (`crm_sync.enqueue(conversation_id=...)`, `crm_filing.file_interaction(conversation_id=...)`, kept through `retry_due`, and `SyncLedger.list(conversation_id=...)` finds the entries), so a failed filing is found from the timeline. ## Filing interactions through the sync ledger

`platform/core/crm_filing.py` runs the filing that `crm_sync.py` tracks: it takes the portable `crm.log-interaction` arguments and an executor (the Tier 0 contact log or an approved upstream executor, which share an `arguments -> result` shape) and records every attempt in the provider-neutral sync ledger. It contains no provider code and is credential-free. The runtime worker wires it to the support mailbox (below); the call path is still the operator-invoked `file-calls` command (#108, #115).

- **One entry per call or message.** The ledger key comes from the channel, the call or message id and the interaction type, so redelivery, a retry and a restart reach the same entry and nothing is filed twice. Tests replay the same interaction through the built-in log and an injected provider-neutral upstream executor and get the same states.
- **Success only on the provider's word.** A result without an `externalObjectRef` is a rejection. A result flagged `duplicate` means the record was already there (for example the first attempt landed and its answer was lost), so the entry is *reconciled* to the existing reference rather than written again.
- **Failures are sorted.** An error carrying a sync `code` keeps it; a `PermissionError` is `unauthorized`; a `ValueError` (bad arguments, an unknown contact) is `rejected` and waits for a person; anything else is a transient `outage` that backs off and, after the ceiling, blocks.
- **No content in the ledger.** `retry_due` takes a `payloads` callable for the interaction to retry (a deployment reads it from its transcript or message store); an entry whose payload is unavailable is skipped and counted, never invented.

**Wired to the support mailbox (worker `crm-sync`).** When `crm` is bound to the Tier 0 contact log, the worker gives `SupportMailbox` a `SyncLedger` (`<data>/crm-sync`), a `PayloadStore` and an executor that is the *governed* `crm.log-interaction` boundary (`GovernedToolRuntime.crm_log_interaction` under `runtime:support-mailbox`: policy, approval and the Action Ledger apply like any other call). Each handled email is filed once, keyed by its thread, so a redelivery files nothing twice. It is filed against a contact only when the sender was verified by the receiving server (SPF/DKIM/DMARC) *and* exactly one contact holds that address (`ContactStore.find_by_email`, an internal read that is not a Tool); an unverified sender, no holder or several holders (a possible duplicate a person must settle) all go to the `unmatched` queue for a person to assign (`client-operator.py contacts review|assign`), and the model never chooses the contact. `PayloadStore` keeps the portable arguments of an interaction that has not been acknowledged yet (contact id, channel, direction, time, a one-line category-and-status summary and a reference, never a message body; 0700 directory, 0600 files, bounded) and deletes them when the CRM acknowledges. The worker's `crm-sync` job (default every 120 s, `intervals.crm-sync`) retries entries past their backoff and, for any entry that is `blocked`, tells the mailbox owner (or `escalateTo`) once. A governed result that is not `executed` (an approval is pending, a person has it, it was denied) is treated as `unauthorized`, so the entry blocks for a person and is never reported as filed. `python3 scripts/client-operator.py crm-sync list|retry <key> --by <person> --project-name <env>` shows state, attempts, error code and the next step (identifiers only) and makes a repaired entry pending again under the named person (ledgered). With no built-in contact log bound the job reports `no-built-in-crm-bound` and nothing is filed.

Open: wiring the same runner to the voice transcript path (call filing is still operator-invoked), real CRMs behind an approved upstream executor, cross-channel timelines and identity linkage, and live proof (#108, #115). Credential-free tests only; no live deployment has exercised this.

## Guided connect step

`platform/core/connect.py` is the credential-free core of connecting a CRM, mailbox or calendar for one named coworker (#110). The operator provisions the provider-side identity and secret elsewhere and passes only the `secret://` reference; this module runs no owner OAuth consent, stores no secret, makes no provider call itself (the read-only test is injected) and is not wired to the interactive CLI.

- **Plan.** For a named Agent, client owner and operator, the plan takes its scopes from the registry's reviewed mapping for the selected portable Tools and refuses a request for more. It carries a digest of everything the owner consents to; `apply` needs that digest back, so consent to one plan cannot be reused for another. Providers that are not shipped, and Tier 0 providers (which need no credentials), are not connectable and the plan says why. A mailbox is `shared` or `delegated`; a `personal` one needs an explicit recorded owner exception.
- **Apply.** The read-only connection test runs first. If it fails nothing is recorded and the failure is ledgered; on success the coworker's own grant is recorded (`provider_grants.py`, so a second coworker never inherits the first one's credential) and the binding fragment (provider, tier, scopes, owner, never a secret) is returned for `merge_binding`, which leaves the input untouched, keeps a live `token_ref` for the same provider and makes replacing a provider explicit.
- **Ledger.** `connection.connect`, `connection.connect-failed` and `connection.disconnect` name the operator and the client owner with identifiers, never a credential, reference or account. `disconnect` revokes one coworker's grant and affects no other.

- **Changing a working connection.** `merge_binding` refuses, unless the caller passes `rescope`, to widen the scopes of a binding that already lists scopes or to change its owner, in addition to the existing explicit `replace` for a provider; `describe_change` shows exactly what a fragment would change. A legacy binding with no `scopes` key is narrowed, not widened, by naming scopes. `replace` moves a coworker to a new grant without leaving it with none: the test and the new grant first (a failure changes nothing), then the injected binding write, then revoking the previous grant. The injected binding writer **must be atomic**: it returns `None`/`True` after durable persistence or raises/returns `False` without changing the binding. An unconfirmed/failed write keeps the previous grant active and revokes the new grant, recording `connection.rolled-back`. If revocation itself fails, `connection.rollback-failed` names the unresolved grant and error *type* (never provider error text or secrets), and the operator must reconcile both grants and the binding before retrying; no rollback success is claimed. A successful write ledgers `connection.replaced` with both grant IDs and reports an old-grant revocation failure as `previousRevoked: false`. A writer that partially persists before failing violates the atomic-writer contract; this helper cannot roll back external writes.

Open: owner OAuth consent and token acquisition, credential storage, a live test, re-running Skill readiness after a change, and the interactive CLI (#110, #86, #129).

Stable operational contract:

- `usage-attribution.schema.json` — canonical non-secret client/Agent/environment/provider and optional cost/trace/subscription/shared-pool dimensions used to correlate runtime consumption with showback and billing. This is platform-generated operational metadata, not client-authored Agent/Skill desired state.

Business teams should depend on the business resource contracts rather than infrastructure details or physical model IDs. Runtime/commercial integrations should depend on the explicit operational contracts rather than inventing provider-specific attribution shapes. Breaking schema changes require a new API version, e.g. `modelgarden.ai/v2`.

## Integration registry and readiness-to-connect boundary

`contracts/v1/integrations.json` is the **single technical inventory** of providers by capability family, connection method/tier, maturity, portable Tools, tracking issue and (for implemented providers) adapter source. Its schema, Tool coverage, adapter existence and live-proof requirements are exercised in tests. **`built-credential-free` means an adapter and automated tests exist; it does not mean a real client tenant, refreshable authorization, or production acceptance has been proven.** No provider is currently marked `live`.

Render the provider directory for review and Confluence sync without maintaining a second manually authored list:

## Shipped-provider activation gate

An EnvironmentBinding naming a provider is not evidence that its connector exists. The
compiler, `client-operator skills` readiness report, non-secret coworker
`platform.capabilities` manifest and Docker deployment now consult
`contracts/v1/integrations.json` to determine **implemented** support. Only
`built-credential-free` or `live` providers with a matching family, correct tier
and an implemented Tier 0 local backend (or, in future, a separately vetted, authorized upstream executor) satisfy a dependency. Currently **only** `text-knowledge`, `built-in-crm`, `built-in-artifacts`, `built-in-files` and `built-in-tickets` qualify; historical Calendar aliases do not activate retired integrations.

A planned HubSpot/Jira/Zoho/SharePoint/Drive provider, an unregistered provider,
or a Tier 0 provider bound at the wrong tier or under the wrong family (for example
`built-in-crm` at tier 1 or under `kb`) **cannot activate a Skill**. The Tier 0
`text-knowledge` (`connectors.kb: {provider: text-knowledge, tier: 0}`) and `built-in-crm`
(`connectors.crm: {provider: built-in-crm, tier: 0}`) providers are shipped credential-free
and do satisfy `kb` and `crm`; they hold no client credential, so they still need approved
content (an approved knowledge file; a person to review the contact log) and have no live proof.
Required capabilities remain blocked, optional ones degrade to the declared
fallback, and production deployment repeats the check even when it receives a
previously compiled desired-state document. A missing or invalid registry
fails closed. This gate verifies shipped adapter presence, **not** client
consent, a current access token, live provider health or completed acceptance
proof. Real OAuth and live proof are still tracked by
[#66](https://github.com/kingyx3/model-garden/issues/66) and
[#86](https://github.com/kingyx3/model-garden/issues/86).

## Provider evidence manifest and go-live gate

Whether a provider may be called live is shown, not inferred. `python3 scripts/provider-evidence.py` (`--format markdown` for review) emits one entry per registry provider: family, tier, method and status; the adapter path and its SHA-256; the automated test files that load that adapter and how many tests they hold (a count of tests in those files, so a broad file is over-counted); the reviewed scope set; the retained live tenant proof and its state; the limitations that still apply; and `goLive`, whether a go-live claim is allowed and every blocker. A go-live claim needs a shipped adapter (`built-credential-free` or `live`), automated adapter tests and, for any provider that reaches a third-party tenant (tier 1 and above), a **valid, unexpired proof for the current adapter** with scopes equal to the reviewed set, and the registry must itself say `live`. A Tier 0 provider reaches no third-party tenant, so it needs tests but no tenant proof and keeps the limitation that no deployment evidence is retained. `provider-evidence.py --go-live <provider>` exits non-zero with the blockers.

Live proof is a retained, redacted file `assurance/provider-proof/<provider id>.json` (the registry's `proof` field names it for a `live` provider) with `schemaVersion`, `provider`, `provedAt`, `expiresAt`, `adapterSha256`, `scopes`, `recordedBy`, `evidence` (run ids or artefact names, never content), `redacted: true` and optional `limitations`. Any other key (a tenant identifier, token or content) makes the proof invalid. A proof is bound to the adapter it proved: changing the adapter file invalidates it until the provider is proven again, and an expired proof blocks go-live without breaking unrelated work. `provider-evidence.py --check` (run by `make contracts` and CI) fails only when a registry claim is untrue now: a `live` provider with no valid proof file, a malformed proof, or a proof for an unknown provider. No provider is live today and no proof file is retained, so every tier 1+ provider is blocked. Producing a proof needs a real tenant and a person; the manifest does not call a provider.

## Enable or disable individual Skills safely

An Agent may list a Skill in `spec.skills` while keeping it off using `spec.disabledSkills`. Example:

```yaml
spec:
  skills: [answer-faq, take-message, book-appointment]
  disabledSkills: [book-appointment]
```

Disabled Skills remain in the non-secret readiness report but are **not** materialized into the Hermes runtime, do not contribute required capabilities, and suppress Tools used exclusively by disabled Skills. Tools shared with enabled Skills remain selected. Removing a Skill from `disabledSkills` is an activation: the ordinary required-capability validation then **fails closed** if its provider is missing. Keep direct Agent instructions aligned with what is enabled; disabling a Skill is not a grant/revocation of an underlying client provider credential.

### Knowledge freshness

A `text-file` KnowledgeSource may carry `reviewBy` (a `YYYY-MM-DD` date). The content may ground answers through that day; afterwards the source is `stale`: `kb.search` returns no documents with reason `source-stale` (it fails closed, the same as a draft), the dependent Skill reports `no-content` with the source's state, and its `remediation` asks the owner to confirm the content and set a later `reviewBy` before recompiling. An impossible date is treated as invalid and refused the same way; omitting the field means the source never goes stale. The worker's `knowledge` job (every 6 hours, `intervals.knowledge`) tells `escalateTo` (else the mailbox owner) once when an approved, usable source is due for review within 14 days and once when it has gone stale, naming only the source and the date, so the coworker's answers do not quietly turn into "I don't know"; with nobody to tell it does nothing. This checks the declared date, not whether the content is actually still true, and external documents and document-level permissions remain #116 work.

### Knowledge content readiness

A Skill that requires `kb` is ready only when the provider is bound **and** the Agent selects at least one usable KnowledgeSource: `status: approved`, an `effectiveDate` that has arrived, and an `audiences` list (if any) that names the Agent. Otherwise the readiness report, `client-operator.py skills`, the compiled `capabilities.skills` and the coworker's `platform.capabilities` show the dependency as `no-content` with each source's state (`draft`, `retired`, `not-yet-effective`, `effective-date-invalid`, `not-for-this-agent`, `not-indexed`) and the Skill is not ready (`canEnable: false`, `skills` exits non-zero). Compilation still succeeds so a draft can be authored and reviewed, and an *optional* `kb` dependency reports the states without blocking. States are non-secret names only; source text never appears. This checks declarations, not document-level permissions or freshness (#116).

**Remediation.** Every blocked Skill also carries one non-secret `remediation`: the action that unblocks it (connect the missing family, approve business knowledge for this coworker, or have the operator reauthorize a failed or revoked connection). It appears in `--readiness`/`client-operator skills` and the compiled `capabilities.skills`, and it names families and commands only, never a secret, scope, account or source content. A Skill that is ready has none. The coworker's `platform.capabilities` answers by who is asking instead (below).

**What the coworker is told depends on who is asking** (`capabilities.caller_view`, `GovernedToolRuntime.capabilities_for_caller`; #111, #110, #116). The operator `remediation` carries shell commands, so it is never handed to the coworker. A verified team member gets each blocked Skill's one `nextStep` in plain words ("Connect calendar: ask your operator or consultant to start the guided connect step for it"; never a command) together with the rest of the manifest. Anyone else (a public caller, an unmapped sender, a call with no attributed person) gets only whether each Skill is ready and the capability family and status, with no provider, grant, knowledge-source name or state, reason or environment name, so the coworker can say truthfully "I can't book appointments here" and nothing about how this client is set up. The tool description tells the coworker to say the step in its own words and to offer a message or a hand-off otherwise.

### Readiness that checks the coworker's own grant

With a per-coworker grant registry present for the environment (`<governance root>/provider-grants/<client>-<environment>.grants.json`, see "Per-coworker provider grants"), `platform/core/grant_readiness.py` overlays it on the sidecar's `platform.capabilities` so a *connected* Skill is ready only when its own Agent holds a usable grant for the bound provider that covers the Tools it selected. A bound Tier 0 dependency is untouched. A required dependency is otherwise `no-grant` (this Agent holds no grant for that provider; another coworker's grant never counts), `grant-unavailable` (every such grant is revoked, expired or failed) or `grant-scope` (the grant lacks selected Tools, which are named), and the Skill is not ready with a one-line `remediation` (provision this coworker's own grant, renew it, or re-scope it); an optional dependency degrades to its fallback tier instead. A healthy grant adds `grant: {state: active|degraded, isolation}` and nothing else: no identity, connection id or secret reference. Scopes are checked per family because the manifest records the Tools the Agent selected per family, not per Skill, so the check errs toward blocking. With no registry the sidecar behaves as before; a registry that exists but cannot be read (or belongs to another tenant) blocks connected Skills rather than being ignored. This is readiness only: Tool calls still use the environment binding until the sidecar resolves grants from attested caller context (#129), and there is no live proof.

### Knowledge change trail

The governed sidecar fingerprints the KnowledgeSources in its compiled desired state (declared fields and the content digest, never the text) and, when it differs from the fingerprint it last applied (a private `knowledge-applied.json` beside the ledger), appends one chained `knowledge.change` operator event before serving: which sources were added, removed or changed and in which fields, the version and first 16 characters of the digest before and after, who deployed it (`MODEL_GARDEN_DEPLOYED_BY`, asserted not authenticated), and the critical changes by name (`newlyApproved`, `approvedContentChanged`, `audienceWidened` (including Skill audiences), `accessWidened` (confidential/restricted content becoming customer-readable), `retired`). A draft being edited is recorded but not critical. An unchanged restart records nothing, the event is written before the new fingerprint is remembered, and a ledger failure stops the sidecar from starting. When the EnvironmentBinding names `governance.owners`, compilation also refuses an `approved` text source whose `metadata.owner` is not on the list (an empty list refuses every approved source); that narrows who may claim ownership of business rules but does not authenticate them.

**Promotion gate and rollback (#116).** `platform/core/knowledge_promotion.py` and `scripts/knowledge-promotion.py` put a gate in front of that trail. A *critical* change (a source becoming approved, approved text or version changing, an Agent/Skill audience widening, or confidential/restricted content becoming more publicly accessible) is promoted only when evals that ran against that exact approved content and visibility passed: `eval-receptionist.py <workspace> --evidence evidence.json` writes the run's result with the version and SHA-256 of every knowledge source it evaluated (also when the run failed), and `knowledge-promotion.py check|promote` accepts it only if it names the expected suite, passed, is recent (default seven days), is not from the future and holds the same digest, version, approved status, classification and exact Agent/Skill audience as the content being promoted, with a true pass flag and integer zero failures. Older evidence without those fields must be regenerated; draft-only or narrower-access evals cannot approve expanded access; when `governance.owners` is named the promoter must be one of them (asserted, not authenticated). Drafts, retirements and removals need no evals. The promotion record (`knowledge-promotion.json`, kept in the client workspace repository so it is reviewed like any other change) holds the promoted snapshot (fields and digests, never text), who and when, a digest of the evidence and the snapshot promoted before. `verify` exits non-zero when what is about to be deployed differs from the promoted snapshot (content changed without a promotion), `rollback` makes the previous snapshot the promoted one and `plan` lists the sources, versions and short digests to restore in the workspace; restoring the text is a repository action, after which `verify` proves it. The eval is the credential-free reference suite, not a model-quality run; nothing here judges whether the rules are true, authenticates the promoter, or is wired into the deploy workflow yet, so a deployment has to run `verify` and `check` itself.

### Status consistency

The integration registry and versioned tests are the authority for implementation status. `python3 scripts/check-status-consistency.py` (run by CI and `make contracts`) fails when a doc calls a built provider planned or unimplemented, calls an unproven provider live, denies capabilities the reference receptionist does declare, or when the Tier 0 providers stop being `built-credential-free` at tier 0 with no live proof. It cannot directly validate Confluence pages. When the registry changes, run `python3 scripts/integration-directory.py --format markdown` and reconcile the [Confluence Integration Directory](https://modelgarden.atlassian.net/wiki/spaces/BA/pages/12189707) against its generated statuses; review the [target architecture](https://modelgarden.atlassian.net/wiki/spaces/BA/pages/11796484) and [receptionist reference](https://modelgarden.atlassian.net/wiki/spaces/BA/pages/1114125) only for misleading implementation claims. Never change `built-credential-free` to `live` without retained client/provider proof. Any Confluence status review should stay lightweight and use the authoritative registry, not a second integration catalog or sync job. The remaining status consistency work is tracked in [#131](https://github.com/kingyx3/model-garden/issues/131).

### Reference receptionist on a zero-stack client

The reference receptionist declares `kb.search`, `crm.create` and `crm.log-interaction` (Tier 0, no third-party account) alongside optional booking definitions; its booking Skill must remain disabled until an upstream route is approved. A client with no calendar sets `disabledSkills: [book-appointment]` and binds only `connectors.kb` (`text-knowledge`, tier 0) and `connectors.crm` (`built-in-crm`, tier 0); the calendar Tools are then suppressed and the bundle renders with no calendar provider. A client can later remove the Skill from `disabledSkills` only after an approved upstream calendar route is proven and bound (planned Tier 2); the Agent and other Skills need no rewrite. Unshipped providers (for example `hubspot`), forged tiers, or a failed connection keep the dependent Skill blocked. `tests/test_reference_compatibility.py` pins both scenarios, and `python3 scripts/eval-receptionist.py` also checks that each scenario's question retrieves the expected approved-knowledge section. The Tier 0 kb/crm path still has no live deployment evidence.

```bash
python3 scripts/client-operator.py skills <private-client-workspace> --environment dev --agent receptionist
```

This prints `ready`, `DISABLED` and `BLOCKED`, dependencies, and registry-backed `connect <family>` guidance without exposing tokens. An intentionally disabled Skill does not block the current deployment; enabling it without its required capability does. The `platform.capabilities` coworker response includes the same per-Skill `enabled`, `ready`, `canEnable` and dependency facts. When a connector is failed or revoked, live runtime health overlays mark dependent required Skills unavailable until a named operator reauthorizes the connection.

Tier 0 `kb` (a business-rules text file) and Tier 0 `crm` (the contact and interaction log) are implemented credential-free; full consent/provisioning (#110) and third-party CRM providers (#93) remain **unimplemented**. The reference receptionist declares both as dependencies and its Skills are ready on the Tier 0 bindings. Do not represent these capability checks as real external provider proof.

## First-class Skillsets

A `Skillset` is a versioned, credential-free catalogue resource (`kind: Skillset`, `metadata.name/owner/version`, `spec.skills` and optional `spec.includes`/`spec.provenance`). Agents pin it under `spec.skillsets: [{name: front-office, version: 1.0.0}]`. Selection **does not** enable any bundled Skill: `spec.enabledSkills` explicitly names active bundled members. Legacy direct `spec.skills` remain enabled unless in `disabledSkills`. Each compiled Agent expands bundles independently and exports a non-secret `skillSelection` summary. Missing/pin-conflicting/cyclic bundle references are errors; disabled members have no executable instructions or exclusive Tools. Bundles cannot introduce connector credentials, Agent-level Tools, or permissions. Changes follow the normal reviewed workspace PR, evaluation and deployment approval path; a prior revision can be redeployed to roll back.


**Opt-in Skill audience boundary (v0.8.135, #111/#116).** A Tier 0 text `KnowledgeSource` may declare `spec.skillAudiences: [answer-faq]` in addition to its Agent `audiences` and caller `classification`. This is a *restriction*, never a grant. A source with `skillAudiences` returns no documents (`source-skill-context-required`) on the currently deployed Hermes MCP route, because that route cannot attest which Skill initiated a Tool call. The activation/readiness manifest likewise marks this source unusable and blocks a dependent Skill; simply naming the Skill in a declaration does not unblock it. A future **trusted, runtime-injected** `skill_resolver` can supply a compiled enabled Skill name with `kb.search` in its own allowed Tools; then retrieval additionally checks the source's exact Skill audience and returns `source-not-for-this-skill` for a mismatch. The model-facing `kb_search` Tool accepts **no** Skill argument. An invalid resolver result fails closed. No resolver is wired into the pinned Hermes deployment; this is a guarded contract prerequisite, not shipped live Skill-scoped retrieval authorization. Locale fallback hints are computed only from sources that pass caller/Agent/Skill authorization, so a restricted source cannot advertise its language to an unauthorized caller. Existing sources without `skillAudiences` retain their Agent/classification checks and behavior. Until upstream attestation is qualified, use separate Agent-scoped sources or keep the Skill blocked; never spoof a Skill identifier from prompts, headers or tool arguments.
